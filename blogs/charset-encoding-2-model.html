Character Encoding (Part 2): The Character Encoding Model

2022-02-20 | Encoding

In the previous article, we explored the digital Babel of pre-Unicode character sets: ASCII, ISO 8859, GB 2312, Big5, Shift JIS, and dozens of other conflicting standards. To understand how Unicode successfully resolved this fragmentation, we must first establish a clear, modern mental model of what "character encoding" actually represents.

The Unicode standard formalizes this through a four-layer character encoding model. Each layer has a distinct, isolated responsibility. Understanding these boundaries is the key to mastering how computers process, store, and display text.

Layer 1: Abstract Character Set (ACS)

The first layer answers a foundational question: what repertoire of characters do we need to support?

An abstract character is a conceptual unit of information used to organize, control, or represent textual data. Simply put, it is a "character" as perceived by humans—independent of how a computer represents it in memory.

For example, the capital letter "A" is an abstract character. The Chinese character "中" (middle) is an abstract character. The "grinning face" emoji "😀" is also an abstract character. These entities exist purely as linguistic or symbolic concepts, separate from any computer code.

The collection of these units is known as the abstract character set (or repertoire). Unicode's repertoire contains over 149,000 abstract characters spanning 168 distinct scripts, alongside mathematical symbols, emojis, and historical writing systems.

Crucially, at this layer, characters have no numerical associations, no byte values, and no binary forms. They are simply an unordered inventory of human communication elements.

Different visual forms (glyphs) of the same abstract character

Layer 2: Coded Character Set (CCS)

The second layer maps the abstract to the mathematical: what numeric index do we assign to each character?

A Coded Character Set maps every abstract character in a repertoire to a unique, non-negative integer. In the Unicode standard, this assigned integer is called a code point. This mapping gives every abstract character a permanent, stable numerical address.

For instance, in the Unicode coded character set:

  • "A" → code point 65 (written as U+0041)
  • "中" → code point 20013 (written as U+4E2D)
  • "😀" → code point 128512 (written as U+1F600)

This mapping is arbitrary but fixed. Once assigned, a code point never changes its meaning. U+0041 will always represent the "Latin Capital Letter A."

A code point is an abstract integer, not a physical byte sequence. The expression U+0041 denotes the integer 65; it does not dictate whether that integer should be stored as the single byte 0x41 or the multi-byte sequence 0x00 0x41. Mapping these abstract integers to physical bytes is the job of the subsequent layers.

Many developers conflate "character set" with "character encoding." When someone refers to the "ASCII character set," they typically mean its Coded Character Set: the mapping of characters to indices 0 through 127. However, a CCS is only one part of an encoding system — it defines the numeric identifiers but does not specify how those integers are stored as binary data on disk.

Layer 3: Character Encoding Form (CEF)

The third layer translates numbers into memory structures: how do we map abstract code points to physical code units?

A Character Encoding Form maps abstract code points to sequences of code units. A code unit is the fundamental bit-width used by an encoding scheme — typically 8 bits (a byte), 16 bits, or 32 bits.

This is where the three primary Unicode encoding forms operate:

UTF-32

The most straightforward encoding form. Every code point is mapped directly to a single 32-bit code unit. Thus, U+0041 becomes the 32-bit value 0x00000041, and U+1F600 becomes 0x0001F600.

Because UTF-32 is a fixed-width encoding, every character occupies exactly 4 bytes. This simplifies string manipulation and indexing (the *n*-th character is always located at byte offset *n* × 4), but it introduces massive storage overhead, as the vast majority of characters in practical text have code points well below U+10000 and thus waste the leading 3 bytes.

UTF-16

UTF-16 uses 16-bit code units. Characters in the Basic Multilingual Plane (BMP, U+0000 to U+FFFF) are represented by a single 16-bit code unit. Code points above U+FFFF (the supplementary planes) are mapped to a pair of 16-bit code units called a surrogate pair.

For example:

  • U+0041 ("A") → one code unit: 0x0041
  • U+4E2D ("中") → one code unit: 0x4E2D
  • U+1F600 ("😀") → two code units: 0xD83D 0xDE00 (a surrogate pair)

UTF-16 is a variable-width encoding: characters are represented by either 2 or 4 bytes.

UTF-8

UTF-8 uses 8-bit code units (bytes) and maps code points using a variable sequence of one to four bytes:

  • U+0000 to U+007F (ASCII range) → 1 byte
  • U+0080 to U+07FF → 2 bytes
  • U+0800 to U+FFFF → 3 bytes
  • U+10000 to U+10FFFF → 4 bytes

For example:

  • U+0041 ("A") → 1 byte: 0x41
  • U+4E2D ("中") → 3 bytes: 0xE4 0xB8 0xAD
  • U+1F600 ("😀") → 4 bytes: 0xF0 0x9F 0x98 0x80

UTF-8 is also a variable-width encoding, but it has a decisive historical advantage: ASCII characters (0–127) are encoded as single bytes identical to standard ASCII. Any legacy ASCII text file is already valid UTF-8, and any legacy ASCII parser can safely process the ASCII portions of a UTF-8 file without error.

To summarize Layer 3: the CEF converts the abstract integer addresses from Layer 2 into binary sequences formatted for CPU memory architectures.

Layer 4: Character Encoding Scheme (CES)

The fourth layer addresses physical serialization: how do we write those code units as a sequential stream of bytes?

A Character Encoding Scheme defines how code units are serialized into bytes for storage or network transmission. While this may seem redundant — computer memory is already structured in bits — a critical problem arises whenever a code unit spans multiple bytes: byte order.

When a code unit is larger than a single byte (such as UTF-16's 16-bit units or UTF-32's 32-bit units), we must define which byte is written first into the stream:

  • Big-Endian (BE): The most significant byte is written first. For example, the UTF-16 code unit 0x4E2D is serialized as the byte sequence 0x4E 0x2D.
  • Little-Endian (LE): The least significant byte is written first. The code unit 0x4E2D is serialized as 0x2D 0x4E.

Different architectures have different native byte orders. Intel x86 and ARM processors are natively little-endian, while standard network protocols default to big-endian. Without an explicit scheme, an application reading a file cannot determine the intended byte order.

Big-endian storage order matches human reading order

To resolve this ambiguity, the standard introduces the Byte Order Mark (BOM): a non-breaking zero-width space code point (U+FEFF) prefixed to the start of a text stream. If a reader parses the leading bytes as 0xFE 0xFF, it deduces the stream is Big-Endian. If it encounters 0xFF 0xFE, it interprets the stream as Little-Endian. (Because the inverse value U+FFFE is a guaranteed non-character, collision is impossible.)

For UTF-8, byte ordering is never an issue because its code units are exactly one byte wide. However, a UTF-8 BOM sequence (the bytes 0xEF 0xBB 0xBF) is sometimes written by Windows-based text editors purely as a signature to flag that the file contains UTF-8 text rather than a legacy local code page.

The encoding scheme layer also manages other serialization realities, such as:

  • Detecting and recovering from truncated byte streams.
  • Encoding binary text for legacy 7-bit mail transport (e.g., Base64 or Quoted-Printable).

Putting It All Together

Let's map out how a single Chinese character, "中" (middle), traverses all four layers of the character encoding model:

  1. Abstract Character Set: "中" exists as an abstract unit of human language, representing the concept of "center" or "middle."
  2. Coded Character Set (CCS): Unicode assigns this abstract character to the unique, permanent code point U+4E2D (decimal 20013).
  3. Character Encoding Form (CEF): This code point is formatted into memory:
    • In UTF-8, it is represented as a sequence of three 8-bit code units: 0xE4 0xB8 0xAD.
    • In UTF-16, it is represented as a single 16-bit code unit: 0x4E2D.
    • In UTF-32, it is represented as a single 32-bit code unit: 0x00004E2D.
  4. Character Encoding Scheme (CES): These units are written to disk:
    • In UTF-8, they are serialized sequentially as bytes: 0xE4 0xB8 0xAD (no byte order concerns).
    • In UTF-16 BE, the bytes are written as: 0x4E 0x2D.
    • In UTF-16 LE, the bytes are written as: 0x2D 0x4E.
    • In UTF-32 BE, the bytes are written as: 0x00 0x00 0x4E 0x2D.

Each layer operates independently. The Abstract Character Set defines *what* we represent. The Coded Character Set assigns *addresses*. The Encoding Form structures those addresses in *memory*. The Encoding Scheme writes those structures as *bytes*.

Why This Model Matters

This division of labor makes it easy to diagnose common encoding bugs:

  • Mojibake (Garbled Text) occurs when a system reads raw bytes (Layer 4) but applies the wrong decoding form (Layer 3). The physical data is perfect, but the software's translation lens is wrong.
  • "UTF-8 vs. UTF-16" is not a debate about the character set (Layer 2). Both formats use the exact same Unicode code points; they simply organize those addresses differently in memory (Layer 3).
  • "Should I include a BOM in UTF-8?" is a Layer 4 serialization concern. UTF-8 never needs a BOM to establish byte order, but legacy editors use it as a file-type marker.
  • "Why is my emoji displaying as a blank box?" can be a Layer 3 issue (where a legacy library fails to parse surrogate pairs or 4-byte UTF-8 sequences) or a Layer 2 issue (where the emoji was minted in a newer version of Unicode than the host operating system supports).
