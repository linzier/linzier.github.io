On the Factory Pattern

2022-03-15 | Design Patterns | Original

Ask 100 interview candidates which design patterns they know, and at least 99 will mention the factory pattern. This tells us two things: the factory pattern is one of the most commonly encountered design patterns for developers, and it's also one of the most intuitive and easiest to understand — both conceptually and in implementation.

But if you probe further — what problem does the factory pattern solve? How does it solve it? What are its drawbacks? When should you not use it? — not everyone can answer clearly.

The Complexity of Software Design

Software is, at its essence, humans instructing machines to handle affairs of the human world. The complexity of the human world inevitably reflects in software.

High school physics tells us: motion is absolute, rest is relative. "The only constant is change itself." It is the motion (dynamism) of things that creates complexity — or in more accessible terms, "the uncertainty of the future." Requirements change endlessly; no software remains static.

The natural consequence of motion is entropy increase — just as your living room inevitably gets messier over time. As software evolves, it inexorably trends toward chaos: old logic changes, new logic is added (and existing bugs are "fixed"), and the system grows increasingly complex and incomprehensible. Bugs multiply. Modifications become harder.

People have an intuitive but mistaken belief: by fixing bugs, we can gradually reduce the system's bug count to zero. Unless the system never needs iteration after release, no matter how fast you type, you can't outpace bug growth (this is especially evident in upper-layer business systems).

Programmers combat software entropy primarily through refactoring and design patterns.

Refactoring rebuilds the system in the future to eliminate or reduce chaos. It's based on the premise that people will have deeper understanding of the system and business in the future than in the past, and that the previous design has reached its limit for accommodating change. In practice, refactoring (especially large-scale) often happens at the system's breaking point.

Design patterns pre-build the system in the present to handle future complexity (change). Design patterns distill common elements from past experience, standardize them (forming patterns), and pursue relative stability in system design — using the unchanging to face the uncertain future.

Design patterns tackle complexity primarily through abstraction and isolation.

Three Types of Factories

Every design pattern addresses software design complexity and pursues stability. The factory pattern belongs to the creational patterns (along with Singleton, Prototype, and Builder), solving the complexity of object creation.

When does object creation have complexity?

  • When a simple new with a few parameters suffices, there's no creation complexity and no need for a factory;
  • When object creation is polymorphic: like creating different subtype objects based on configuration, with multiple if-else branches in the creation code;
  • When the creation process itself is complex: even though no different subtypes are needed, creating the object requires reading config files, fetching remote data, etc.

Before diving deeper, let's briefly outline the three factory forms (slightly different from GoF's classification):

  • Simple Factory: Create a static method in the target class for creating instances, or extract that static method into a dedicated factory class;
  • Factory Method: An upgrade to Simple Factory. Define a factory interface; each factory implementation returns a specific subtype instance of the target class/interface. Factory Method addresses the potential complexity of Simple Factory, making the factory itself more aligned with the Open-Closed Principle and Single Responsibility Principle;
  • Abstract Factory: An upgrade to Factory Method. It solves multi-dimensional complexity in the target instances, preventing factory classes from exploding alongside the number of target classes. In Factory Method, one factory creates one type of instance. In Abstract Factory, one factory creates multiple types of instances.

The theory can be dizzying. The key takeaway: in terms of both the factory's own complexity and the complexity of the problem it solves, Simple Factory < Factory Method < Abstract Factory (each is a special case of the next, each is an upgrade of the previous). Note the two dimensions of complexity here — this foreshadows the usage principle: solve problems with the simplest tool possible; only upgrade when the problem truly demands it.

Now let's see how the factory pattern uses abstraction and isolation to solve object creation complexity.

Simple Factory

Suppose we're building an online transaction system for a gas station. Customers can purchase fuel, convenience store items, and virtual goods (like coupons). The ordering process involves three classes (simplified; assuming one order purchases one type of good): Transaction, Order, and Goods. Transaction creates Order, and Order depends on Goods.

Suppose Goods creation is complex — it requires combining multiple related objects and fetching external information (product details, inventory, etc.).

There are two ways Order can depend on Goods:

  1. Create Goods inside Order (passing in goodsId from outside);
  2. Inject the Goods object through the constructor.

With the first approach, Order creates Goods internally:

class Order {
    private $goods;

    public function __construct($goodsId) {
        // Complex creation logic embedded here
        $this->goods = new Goods($goodsId);
        // ... more setup code
    }
}

The constructor contains large blocks of creation code, violating best practices. We'd typically extract a separate method:

class Order {
    private $goods;

    public function __construct($goodsId) {
        $this->goods = $this->createGoods($goodsId);
    }

    private function createGoods($goodsId) {
        // Complex creation logic
        return new Goods($goodsId);
    }
}

Slightly better, but at least three problems remain:

  1. Order takes on the responsibility of creating Goods (and it's complex work that may need future changes), violating the Single Responsibility Principle;
  2. Order must understand Goods's construction details, violating the Law of Demeter and breaking encapsulation;
  3. Other places creating Goods must do the same, reducing maintainability (or we make Order's createGoods() public for others to call, but this creates unnecessary dependencies and makes code harder to understand).

Law of Demeter (also called the Least Knowledge Principle): a class should know as little as possible about other classes. An object should have minimal knowledge of other objects.

To solve these problems, we move createGoods() out of Order and into Goods itself, letting Goods be responsible for creating itself. This encapsulates the creation details (complex construction is handled internally by Goods):

class Goods {
    public static function create($goodsId) {
        // Complex creation logic, encapsulated within Goods
        return new Goods($goodsId);
    }
}

This solves the encapsulation problem. Future changes to Goods's creation logic only require modifying Goods itself. Many projects implement Simple Factory this way — it's simple enough and maintains reasonable design stability.

Now let's look at the second approach: injecting Goods into Order via dependency injection. Now Goods must be created in Transaction. The most direct implementation:

class Transaction {
    public function execute() {
        $goods = new Goods($goodsId); // Complex creation here
        $order = new Order($goods);
        // ...
    }
}

Same problems as before: Transaction takes on Goods creation, violating Single Responsibility. Future changes to creation logic require modifying Transaction's code (and worse, ClassX and ClassY might also be creating Goods in multiple places).

The fix: move creation logic into Goods itself. But is that always the right answer?

It depends. If Goods is merely complex to create (manageable complexity that doesn't severely pollute Goods), and creation logic isn't expected to change, then putting it inside Goods is fine (many real projects do this). But if creation involves very complex assembly and is expected to change, this complexity affects Goods's own stability. Fundamentally, having Goods create itself violates Single Responsibility — "creation" is the consumer's responsibility, not the provider's.

So we have a contradiction: we don't want consumers (Transaction and Order) to know about Goods's details (affecting their stability), but we also don't want the provider (Goods) to create itself (affecting its stability). How do we resolve this?

The answer: introduce a third party — a factory class — encapsulating creation complexity in an independent, single-purpose class.

class GoodsFactory {
    public static function create($goodsId) {
        // Complex creation logic isolated here
        return new Goods($goodsId);
    }
}

Now, changes to Goods creation logic only require modifying GoodsFactory — no changes to Transaction, Order, or Goods. This is Simple Factory.

Here we see the factory pattern solving creation complexity through isolation: the complexity of creating Goods (its uncertainty, its future changes) is placed in a separate, single-responsibility factory class GoodsFactory, isolating the instability from Transaction, Order, and Goods, ensuring their design stability.

Factory Method

The previous example didn't showcase abstraction well (though broadly, the factory itself provides abstraction of creation logic, we're focused on abstraction in the narrower sense).

Recall: customers can buy fuel, convenience store items, or virtual goods like coupons. A better design abstracts Goods into an interface with different implementations:

interface GoodsInterface {
    // ...
}

class Fuel implements GoodsInterface { }
class NonOil implements GoodsInterface { }
class Coupon implements GoodsInterface { }

We change Order's dependency from the concrete Goods to the interface GoodsInterface, implemented by Fuel, NonOil, and Coupon. We'd typically inject the implementation via dependency injection:

class Transaction {
    public function execute($type, $goodsId) {
        // Big if-else to create the right GoodsInterface implementation
        if ($type == 'fuel') {
            $goods = new Fuel($goodsId);
        } elseif ($type == 'nonoil') {
            $goods = new NonOil($goodsId);
        } elseif ($type == 'coupon') {
            $goods = new Coupon($goodsId);
        }
        $order = new Order($goods);
        // ...
    }
}

We see a big if-else block in Transaction for creating GoodsInterface instances. Based on our earlier discussion, we should extract this into a factory class:

class GoodsFactory {
    public static function create($type, $goodsId) {
        if ($type == 'fuel') {
            return new Fuel($goodsId);
        } elseif ($type == 'nonoil') {
            return new NonOil($goodsId);
        } elseif ($type == 'coupon') {
            return new Coupon($goodsId);
        }
    }
}

What's wrong with this Simple Factory?

When we abstract Goods into the interface GoodsInterface, it usually signals significant future variability (many potential product types). We add the abstraction layer (interface) to improve design stability (making other classes depend on the stable interface rather than unstable implementations). But this also means we'll constantly modify the factory class, adding more if-else branches. GoodsFactory becomes unstable. Especially when each implementation's creation is complex, the factory itself becomes complex.

Using the same approach we used for Goods, we add another abstraction layer (interface) to solve the factory's own problems.

We extract a FactoryInterface from GoodsFactory:

interface FactoryInterface {
    public function create($goodsId);
}

class FuelFactory implements FactoryInterface {
    public function create($goodsId) {
        return new Fuel($goodsId);
    }
}

class NonOilFactory implements FactoryInterface {
    public function create($goodsId) {
        return new NonOil($goodsId);
    }
}

class CouponFactory implements FactoryInterface {
    public function create($goodsId) {
        return new Coupon($goodsId);
    }
}

Wait — now the factories comply with the Open-Closed Principle, but how do we use them? Like this?

class Transaction {
    public function execute($type, $goodsId) {
        if ($type == 'fuel') {
            $factory = new FuelFactory();
        } elseif ($type == 'nonoil') {
            $factory = new NonOilFactory();
        } elseif ($type == 'coupon') {
            $factory = new CouponFactory();
        }
        $goods = $factory->create($goodsId);
        $order = new Order($goods);
        // ...
    }
}

Are you kidding? Transaction hasn't fundamentally changed! We've just moved the if-else from creating goods to creating factories. Transaction still has a bunch of if-else unrelated to ordering (it's object creation logic), violating Single Responsibility. Every time we add a new factory, we must modify Transaction — even though Transaction should have nothing to do with goods or factory changes.

So the Factory Method pattern needs one more piece: a "factory of factories" that encapsulates the "factory creation" logic:

class GoodsFactoryContainer {
    public static function getFactory($type): FactoryInterface {
        if ($type == 'fuel') {
            return new FuelFactory();
        } elseif ($type == 'nonoil') {
            return new NonOilFactory();
        } elseif ($type == 'coupon') {
            return new CouponFactory();
        }
    }
}

This is the Factory Method pattern.

Now Transaction and each factory are stable, with sufficiently single responsibilities and good extensibility. The only unstable element is GoodsFactoryContainer — or rather, we've transferred the instability from Transaction and Order into GoodsFactoryContainer.

In system design, instability can only be transferred, never eliminated. What we truly aim for is minimizing the impact of instability, maximizing overall design stability.

Since instability can only be transferred, what's the point of moving it?

In our example, goods creation is the unstable factor (stemming from real-world business uncertainty). The variety of goods causes instability in goods factories. Our job is to extract this instability from the relatively stable ordering logic, abstract it behind stable interfaces, have business logic depend on those interfaces, and then encapsulate the implementation details in a container. This way, changes in goods creation logic don't affect ordering logic code.

Notice the code in Transaction:

$factory = GoodsFactoryContainer::getFactory($type);
$goods = $factory->create($goodsId);

These two lines embody programming to interfaces, not implementations.

Order depends on GoodsInterface — who provides the implementation? FactoryInterface. Who provides FactoryInterface's implementation? GoodsFactoryContainer.

When we need to adjust goods creation logic in the future, no modifications will cross the boundary of GoodsFactoryContainer — we only modify GoodsFactoryContainer (and its internal dependencies). And GoodsFactoryContainer exists precisely for this purpose. So changes in goods creation logic don't violate Single Responsibility or Open-Closed (if those changes forced modifications to Transaction or Order, that would violate Open-Closed, since goods creation has nothing to do with those classes' responsibilities).

Through abstraction and isolation, the factory pattern elegantly solves object creation complexity — with one caveat: if the target class/interface has multi-dimensional variability leading to many implementations (and correspondingly many factory classes), this causes a class explosion that seriously hurts maintainability. For example, if the target interface has 2 dimensions with 3 possibilities each, we get 3² = 9 classes and 9 factories. This is where Abstract Factory helps — it reduces 2 dimensions to 1 by having each factory create all instances for one dimension (instead of just one type). If each factory handles 3 types of instances, we only need 3 factories.

In practice, I've never used such a complex pattern (so I won't provide an Abstract Factory implementation here). If a thing needs inheritance hierarchies along multiple dimensions, it easily causes class explosion (one reason inheritance is criticized). A better approach is often composition over inheritance (like using the Decorator pattern).

Summary

The factory pattern is widely used in practice. I'm sure everyone has encountered a classic example: the IoC container. An IoC container is essentially a super-factory responsible for creating objects across the entire system. It automatically resolves complex dependency relationships, and we can decide at the outermost layer (configuration files) which implementation class to use for a given interface — exactly what factories excel at.

When using the factory pattern in practice, follow the KISS principle (Keep It Simple and Stupid). Start with Simple Factory. In the first version of a system, our understanding of concepts and structures isn't deep. Jumping straight to a "big knife" often leads to over-engineering. Believe that "there is no silver bullet" in software design — every design pattern can cost readability, usability, and even maintainability. The factory pattern is no exception (Factory Method introduces a "factory of factories," which itself adds complexity). As the system iterates and we refactor, our understanding deepens. Only when we genuinely identify the problem should we adopt more complex solutions.

To summarize:

  1. Software design complexity originates from the complexity of the real world;
  2. Software systems follow the law of entropy increase — trending toward chaos over time. Design patterns and refactoring combat this — they are anti-entropy processes;
  3. The factory pattern solves object creation complexity;
  4. Specifically, it does so through abstraction and isolation;
  5. In complexity: Simple Factory < Factory Method < Abstract Factory. Start simple; avoid over-design;
  6. The goal of system design is to pursue stability;
  7. Instability in a system can only be transferred, never eliminated. Isolate it to minimize the impact of change, maximizing overall design stability.
