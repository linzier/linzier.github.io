REST as an Architectural Style — What Exactly Is It?

2021-12-15 | Architecture

Ask any backend developer to define REST, and you will hear “clean URLs” or “using HTTP verbs instead of routing everything through POST.” Not wrong, but barely scratching the surface. REST is not a protocol, not a library, and not a URL style guide. It is an architectural style — a set of constraints that, applied together, produce a distributed system with desirable properties.

The term was coined by Roy Fielding in his 2000 doctoral dissertation at UC Irvine. Fielding was not merely an academic — he was a principal author of the HTTP specification (RFC 2616) and a co-founder of the Apache HTTP Server project. When he wrote about how the web should work, he spoke from direct experience.

The Six Constraints of REST

Fielding defined REST through a set of architectural constraints. A system is “truly RESTful” only if it satisfies all of these constraints. Drop one, and you no longer have REST.

1. Client-Server Separation

The client and the server operate on a separation of concerns. The client manages user interface and presentation, while the server handles data storage, business logic, and security. This decoupled boundary allows each component to evolve independently. The client does not need to know how the server stores data, and the server does not need to know how the client renders its UI.

This is the most basic constraint, and nearly every modern API satisfies it. It establishes the foundation for everything that follows.

2. Stateless

Every request from the client to the server must contain all the information necessary to understand and process that request. The server must not store any session state between requests. Authentication credentials, pagination tokens, filtering parameters — everything travels with the request.

This constraint has profound implications for scalability. If the server does not maintain session state, any server in a cluster can handle any request. You can add or remove servers at will. Load balancing becomes trivial. Consequently, statelessness is a critical engineering asset.

The application still has state. The user is logged in; the shopping cart has three items. That state lives on the client side (or in a database), not in the server’s memory between requests.

3. Cacheable

Responses must explicitly declare themselves as cacheable or non-cacheable. When a response is cacheable, the client (or an intermediary) can reuse it for subsequent identical requests, reducing latency and server load.

This constraint leverages HTTP caching: Cache-Control, ETag, Last-Modified, Expires. A well-designed REST API uses these headers aggressively, because every cached response is a request that never reaches the server.

4. Uniform Interface

The most important and most frequently violated constraint. The uniform interface has four sub-constraints:

4a. Identification of Resources

Every resource is identified by a unique URI. A resource is anything you expose as an addressable entity: a user, an order, a blog post, a search result collection. /users/42 identifies a specific user; /orders?status=pending identifies a collection.

Resources are nouns, not verbs. /getUser is not RESTful. /users/42 is.

4b. Manipulation of Resources Through Representations

When the client holds a representation of a resource (say, a JSON document describing a user), it has enough information to modify or delete that resource on the server. The representation carries the resource’s current state, and the client sends modified representations back to the server to effect changes.

4c. Self-Descriptive Messages

Each message must contain enough metadata for the recipient to understand how to process it. The Content-Type header tells you the media type. The HTTP method tells you the intent. The status code tells you the result. The message should not require out-of-band documentation to be understood.

4d. HATEOAS (Hypermedia As The Engine Of Application State)

This is the constraint most developers ignore, and it most clearly separates REST from ordinary HTTP APIs.

HATEOAS means the client interacts with the service entirely through hypermedia provided by the server. The client does not hard-code URI patterns. The server’s responses include links that tell the client what it can do next.

When browsing a website, you do not need to know the next URL in advance. You click a link, and the server guides you. A RESTful API operates the same way.

A RESTful API response might look like this:

{
  "id": 42,
  "name": "Alice",
  "links": [
    { "rel": "self", "href": "/users/42" },
    { "rel": "orders", "href": "/users/42/orders" },
    { "rel": "update", "href": "/users/42", "method": "PUT" },
    { "rel": "delete", "href": "/users/42", "method": "DELETE" }
  ]
}

The client discovers available actions from the response, not from hard-coded URL patterns.

5. Layered System

The client cannot tell whether it is connected directly to the origin server or to an intermediary. Load balancers, reverse proxies, CDN caches, API gateways — these layers sit between the client and the origin server transparently.

This constraint enables the infrastructure flexibility that modern deployments require. You can add caching layers, security filters, and load balancers without changing client or server code.

6. Code on Demand (Optional)

This is the only optional constraint. The server can temporarily extend the client’s functionality by transmitting executable code. JavaScript in web pages is the canonical example: the server sends HTML plus JavaScript, and the browser executes it.

Most REST APIs omit this constraint, and that is acceptable. Its absence does not disqualify an API from being RESTful.

The Reality: Most “REST APIs” Are Not RESTful

The uncomfortable truth: the vast majority of APIs branded as RESTful are not. They violate multiple core constraints, often without their designers realizing it.

Common violations include:

  • No HATEOAS. Clients hard-code URL patterns like /api/v1/users/{id}/orders. The server never provides navigational links. This is the most widespread violation, and it is also the most consequential — it couples clients to the server’s URL structure, making evolution difficult.
  • RPC-style endpoints. Endpoints like /api/getUserOrders or /api/processPayment are not RESTful. They describe operations, not resources. They use verbs where REST requires nouns.
  • Stateful sessions. Using server-side sessions or cookies to maintain authentication state violates the stateless constraint. Token-based authentication (JWT, OAuth bearer tokens) is the RESTful alternative.
  • Ignoring cache headers. Every response returns Cache-Control: no-cache, defeating one of REST’s key scalability features.
  • Non-uniform interfaces. Different endpoints use different response formats, different error structures, different naming conventions. The uniform interface constraint exists to prevent this.

Does It Matter?

Does this distinction matter? Roy Fielding has expressed frustration over how the term “REST” has been co-opted to mean little more than “HTTP with JSON.” When an API is branded as RESTful, developers assume the guarantees REST delivers — scalability, generality, independent deployability, and cache-driven latency reduction.

Many successful APIs violate REST constraints deliberately. Dropping HATEOAS simplifies client development. RPC-style endpoints can be more intuitive for action-oriented workflows. The question is not “Is this RESTful?” but “Do we understand the trade-offs?”

Deviate from REST consciously. Know which constraints you are relaxing and why. Do not call it REST when it is not.

Summary

REST is an architectural style defined by Roy Fielding in his 2000 doctoral dissertation. It consists of six constraints:

  1. Client-Server Separation — distinct concerns, independent evolution.
  2. Stateless — every request is self-contained.
  3. Cacheable — responses declare their cacheability.
  4. Uniform Interface — resource identification, representation-based manipulation, self-descriptive messages, HATEOAS.
  5. Layered System — intermediaries are transparent to the client.
  6. Code on Demand (optional) — the server can extend the client with executable code.

Most APIs that call themselves REST violate several of these constraints. Understanding the constraints helps you make informed architectural decisions — whether you follow them or deviate.
