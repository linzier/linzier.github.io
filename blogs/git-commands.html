Git Common Commands Reference

2020-04-26 | Tools

Three Versions of Branches

When working with Git, it is crucial to recognize that there are effectively three "versions" of any given branch at any moment:

  1. Remote branch — The source-of-truth branch as it exists on the remote server (e.g., GitHub or GitLab).
  2. Remote-tracking branch (remote snapshot) — A local, read-only reference that acts as a snapshot of the remote branch's state. Typically named origin/branch-name, it is updated only when you run git fetch or git pull, reflecting the remote state at the time of your last fetch.
  3. Local branch — Your active workspace branch on your local machine, where you edit files and make commits.

Understanding the distinction between these three is crucial for avoiding confusion when pushing, pulling, and merging.

Repository = Version Control + Working Directory

A Git repository is composed of two main parts:

  • The version control database (the .git directory), which stores all commits, branches, tags, and metadata.
  • The working directory, which is the checked-out set of files you actually edit.

Three Key Areas

  • Working Directory — Your local filesystem where you actively edit files.
  • Staging Area (Index) — An intermediate draft area where you prepare changes before committing. You use git add to register changes here.
  • Repository (Git Directory) — Where committed, immutable snapshots are permanently stored under version control.

The typical workflow is: edit files in the working directory, stage changes in the staging area, then commit them to the version area.

The .git Directory Overview

The .git directory is the heart of a Git repository. Here are its key components:

  • FETCH_HEAD — records the branches that were fetched from the remote during the last git fetch operation.
  • HEAD — a reference to the currently checked-out branch. It typically contains a pointer like ref: refs/heads/main.
  • ORIG_HEAD — created before operations that move HEAD (such as merge, rebase, or reset), allowing you to recover the previous position.
  • config — repository-level configuration settings (remotes, branch tracking, etc.).
  • hooks/ — client-side or server-side scripts that run at certain points in the Git workflow (pre-commit, post-merge, etc.).
  • logs/ — reflog data that records all updates to branch tips, useful for recovery.
  • objects/ — the object database containing all content (blobs), directory structures (trees), commits, and tags, stored by their SHA-1 hash.
  • refs/ — pointers to commit objects, organized into heads/ (local branches), remotes/ (remote-tracking branches), and tags/.

Local and Remote Repositories

Cloning a Repository

git clone <url>

This creates a full local copy of a remote repository, including all history and branches.

Initializing a New Repository

git init

Creates a new Git repository in the current directory.

Adding a Remote

git remote add origin <url>

Links a local repository to a remote server. The name origin is a convention, not a requirement.

Creating Branches from Remote

To create a local branch that tracks a remote branch:

git checkout -b <local-branch> origin/<remote-branch>

Or, if the local branch name matches the remote branch name:

git checkout <branch-name>

Git will automatically set up tracking if there is exactly one remote branch with that name.

git pull: Rebase vs Merge

At its core, git pull is a shorthand command that executes git fetch followed immediately by either git merge or git rebase.

Merge Mode (Default)

git pull origin <branch>

This fetches the remote changes and creates a merge commit to combine them with your local branch, resulting in a non-linear history.

Rebase Mode

git pull --rebase origin <branch>

This fetches remote updates and replays your local, unpushed commits on top of the updated remote branch, yielding a clean, linear commit history.

You can set rebase as the default behavior for a branch: git config branch.<name>.rebase true

Merging Branches: Best Practices

When merging a feature branch into the main branch, it is recommended to use the --no-ff flag:

git checkout main
git merge --no-ff feature-branch

The --no-ff flag forces Git to create a merge commit even when a fast-forward merge would be possible. This preserves the history of the feature branch as a distinct unit of work, making it easier to understand the project history and to revert entire features if needed.

git diff: Various Comparisons

Git provides many ways to compare changes:

  • git diff — shows unstaged changes (working directory vs staging area).
  • git diff --staged — shows staged changes (staging area vs last commit).
  • git diff HEAD — shows all changes (working directory vs last commit).
  • git diff branch1 branch2 — compares two branches.
  • git diff commit1 commit2 — compares two specific commits.
  • git diff --stat — shows a summary of changes (files changed, insertions, deletions).

Reverting Changes

Discarding Working Directory Changes

git checkout -- <file>

This discards uncommitted changes in the working directory, restoring the file to the staging area version.

Unstaging Files

git reset HEAD <file>

This moves a file from the staging area back to the working directory (unstages it).

Resetting to a Previous Commit

git reset --hard <commit>

This resets both the staging area and the working directory to match the specified commit, discarding all changes after it. Use with caution.

Squashing Commits with Interactive Rebase

To combine multiple commits into one:

git rebase -i HEAD~N

This opens an editor showing the last N commits. You can mark commits with squash (or s) to combine them with the previous commit, or fixup (or f) to discard the commit message. This is useful for cleaning up a messy commit history before pushing.

File History: git blame

git blame <file>

This shows the last commit that modified each line of a file, along with the author and date. It is invaluable for understanding why a particular line was changed and who made the change.

Git Log: Various Options

The git log command has many useful options:

  • git log --oneline — compact one-line-per-commit view.
  • git log --graph — shows the branch structure as an ASCII graph.
  • git log --all — shows all branches.
  • git log -p — shows the full diff for each commit.
  • git log --author="name" — filters by author.
  • git log --since="2020-01-01" — filters by date.
  • git log --format="%h %s (%an, %ar)" — custom output format.
  • git log --follow <file> — tracks a file across renames.

Cherry-pick

git cherry-pick <commit>

This applies a specific commit from another branch onto the current branch. It is useful when you want to bring in a particular fix or feature without merging the entire branch.

Reverting Merges

Reverting a merge commit requires special care because a merge has two parents:

git revert -m 1 <merge-commit>

The -m 1 flag specifies which parent to keep (usually 1, which is the branch you merged into). This creates a new commit that undoes the changes introduced by the merge.

Note: after reverting a merge, if you later want to re-merge the same branch, you must first revert the revert commit, otherwise Git will think those changes are already included.

Deleting Branches

Local Branch

git branch -d <branch>

Use -D (capital) to force-delete an unmerged branch.

Remote Branch

git push origin --delete <branch>

Git Flow

Git Flow is a branching model that defines a structured workflow:

  • main/master — production-ready code.
  • develop — integration branch for features.
  • feature/* — new features branched from develop.
  • release/* — preparation for production releases.
  • hotfix/* — urgent fixes for production.

This model works well for projects with scheduled releases but can be overly complex for continuous deployment environments.

Batch Deleting Branches

To delete multiple local branches that have already been merged:

git branch --merged | grep -v "main\|master\|develop" | xargs git branch -d

To delete multiple remote branches:

git branch -r --merged | grep "origin/feature-" | sed 's/origin\///' | xargs -I {} git push origin --delete {}

Line Ending Issues: CRLF vs LF

Different operating systems use different line endings:

  • Windows: CRLF (\r\n)
  • Linux/macOS: LF (\n)

When developers on different platforms collaborate, line ending mismatches can cause spurious diffs and build failures. Git provides the core.autocrlf setting to handle this:

  • Windows: git config --global core.autocrlf true — converts LF to CRLF on checkout, and CRLF back to LF on commit.
  • Linux/macOS: git config --global core.autocrlf input — converts CRLF to LF on commit, but does not change line endings on checkout.

A better approach is to use a .gitattributes file in the repository root to enforce consistent line endings per file type:

* text=auto
*.js text eol=lf
*.py text eol=lf
*.bat text eol=crlf
*.png binary

This ensures that all team members use the same line endings regardless of their operating system, eliminating an entire class of cross-platform issues.
