PHP Development Standards: In Practice

2020-04-26 | PHP

Coding standards are not about aesthetics; they are about reducing cognitive load. When every file in a codebase adheres to the same conventions, developers spend less time parsing formatting and more time understanding business logic. Standards represent a upfront tax on discipline that pays massive dividends in long-term maintainability. Below is a practical, battle-tested set of PHP development standards designed for modern, high-velocity engineering teams.

Part 1: Code Format

The formatting guidelines below extend PSR-1, PSR-2, and PSR-12 with pragmatic, project-specific refinements. The primary goal is total consistency: any developer should be able to open any file and immediately feel at home.

Files

  • Encoding: UTF-8 without BOM. The BOM (Byte Order Mark) introduces invisible noise that disrupts headers, session initialization, and output buffering. There is no legitimate reason to include it in modern environments.
  • Closing tag: Strictly omit the closing ?> tag for files containing exclusively PHP code. This prevents trailing whitespace from being flushed to the output stream, avoiding frustrating "headers already sent" errors.
  • One file, one class: Each class must reside in its own dedicated file, named precisely after the class itself. This is not just a stylistic rule — it is a structural prerequisite for PSR-4 autoloading.

Lines

  • Maximum line length: 80 characters. Lines exceeding this limit must be wrapped or split across multiple lines. This is not a historical artifact of 80-column terminals; rather, it keeps code readable during code reviews, side-by-side git diffs, and on smaller screens.
  • No trailing whitespace: Trailing spaces are invisible noise. They pollute git diffs and signal a lack of craftsmanship. Configure your editor to strip trailing whitespace automatically on save.
  • Line endings: Use Unix-style line feeds (LF, \n) exclusively. Do not commit Windows-style CRLF line endings.

Indentation

  • 4 spaces. Do not use tabs or 2-space indentation. Tabs render inconsistently across different editors and code viewers, whereas spaces guarantee visual predictability everywhere.

Naming Conventions

  • Classes: PascalCase (upper camel case). Examples: UserController, OrderRepository, PaymentGateway.
  • Methods: camelCase (lower camel case). Examples: getUserById, calculateTotal, isValid.
  • Constants: UPPER_SNAKE_CASE. Examples: MAX_RETRY_COUNT, DEFAULT_PAGE_SIZE, STATUS_ACTIVE.
  • Variables: $camelCase. Strive for descriptive variable names. While $user is perfectly acceptable, single-character names like $u are forbidden. Avoid vague terms like $data — opt for $userData or $orderPayload instead.
  • Boolean variables and methods: Always prefix with is, has, can, or should. Examples: $isActive, hasPermission(), canExecute(). This makes the variable's intent immediately apparent at the call site.

Control Structures

  • Insert exactly one space after control structure keywords (if, for, while) and one space before the opening brace.
  • Place the opening brace on the same line as the control structure keyword.
  • Place the closing brace on its own line, aligned vertically with the control structure keyword.
  • Always use braces, even for single-line blocks. Single-line statements like if ($x) doSomething(); are strictly forbidden. This is a prominent maintenance hazard — a developer will eventually append a second statement and inadvertently bypass the conditional check.
  • Write elseif as a single word, not else if.
// Correct
if ($condition) {
    doSomething();
} elseif ($otherCondition) {
    doSomethingElse();
} else {
    doDefault();
}

// Forbidden
if ($condition) doSomething();
if ($condition)
    doSomething();

Braces and Spacing

  • Function and method declarations: place the opening brace on the next line (following PSR-2/12 conventions for class methods).
  • Function calls: omit any spaces between the function name and the opening parenthesis.
  • Binary operators: place exactly one space on each side (use $a + $b, not $a+$b).
  • Unary operators: omit spaces between the operator and its operand (use !$flag, not ! $flag).
  • Commas: always follow a comma with a single space (e.g., foo($a, $b, $c)).
  • Array declarations: use the short array syntax [] exclusively; never use the legacy array() construct.

Closures (Anonymous Functions)

  • Add a single space after the function keyword and before the use keyword.
  • Place the opening brace on the same line.
  • The use clause imports variables from the parent scope.
$greet = function ($name) use ($defaultGreeting) {
    return $defaultGreeting . ', ' . $name;
};

Comments

  • Doc comments: Use structured DocBlocks (/** ... */) for all classes, methods, and properties. Ensure accurate @param, @return, and @throws annotations are provided.
  • Inline comments: Use single-line comments (//). Place the comment on the line immediately preceding the target code block, rather than appending it inline (except for very brief notes).
  • Write comments in English. Code comments must be written in English. This ensures that the codebase remains globally accessible to all developers and automated analysis tools.
  • Document the "why," not the "what." Code describes the mechanism; comments must explain the intent. If a comment merely restates what the code does, the code should be rewritten for clarity, and the comment removed.

Part 2: Program Design

While formatting defines the surface structure, program design dictates system behavior, error resilience, state integrity, and API quality.

Exceptions

  • Leverage exceptions to signal exceptional outcomes. Never return error codes, status strings, or false to indicate a failure. Exceptions force callers to actively handle the failure or allow it to propagate safely; return values, by contrast, are easily ignored.
  • Exception handling in the controller layer: At the entry point (the HTTP controller or CLI command), catch exceptions and translate them into appropriate HTTP status codes or CLI exit codes. The controller serves as the boundary between the system's internal exceptions and external error models.
  • Throw specific, domain-driven exceptions. Avoid throwing generic, uninformative instances of \Exception. Instead, create precise, semantic exceptions such as UserNotFoundException, InsufficientBalanceException, or PaymentGatewayTimeoutException.
  • Include rich contextual details. An exception message must provide sufficient diagnostic detail to isolate the issue without forcing a developer to step through code. Embed key identifiers, the attempted operation, and relevant state boundaries.

Status and Error Codes

  • Define error codes as explicit constants. Every distinct error state must be mapped to a named, immutable constant. Magic numbers or hardcoded strings are strictly forbidden.
  • Maintain uniqueness. Each unique error scenario must correspond to a distinct, unique code. Reusing error codes across different failures makes log aggregation and automated monitoring impossible.
class ErrorCode
{
    public const USER_NOT_FOUND       = 10001;
    public const USER_ALREADY_EXISTS  = 10002;
    public const INVALID_EMAIL_FORMAT = 10003;
    public const INSUFFICIENT_BALANCE = 20001;
    public const PAYMENT_TIMEOUT      = 30001;
}

Logging

  • Adhere to PSR-3. Always consume the standard PSR-3 logger interface. This keeps your logging infrastructure decoupled from concrete backends like Monolog or Logstash.
  • Prefer application-level logging. Log operations at the application/service boundary rather than deep within infrastructure layers. Avoid logging every database query; instead, log significant domain lifecycle events and transactional outcomes.
  • Utilize accurate log levels. Restrict ERROR for incidents requiring immediate intervention. Use WARNING for unexpected, non-fatal anomalies. Reserve INFO for major lifecycle transitions and business milestones, and use DEBUG strictly for diagnostics. Avoid standardizing on generic INFO logs.
  • Ensure structured logging. Leverage context arrays instead of interpolating variables into log messages. Use $logger->error('Payment processing failed', ['orderId' => $id, 'error' => $e->getMessage()]) instead of $logger->error("Payment processing failed for order $id: " . $e->getMessage()).

Caching

  • Adhere to PSR-16 (Simple Cache). Consume the PSR-16 cache interface to keep your application logic independent of storage backends (such as Redis, Memcached, or in-memory arrays).
  • Always specify a explicit TTL. Every cached entry must be bound to a definitive Time-to-Live. Caching without a TTL introduces silent memory leaks and stale state issues. Tailor TTL boundaries to data volatility: 5 minutes for dynamic data, 1 hour for moderate stability, and 24 hours for near-static lookup tables.
  • Implement clear invalidation policies. Standardize on how entries are evicted when underlying entities change — whether via immediate deletion on write, event-driven listeners, or key versioning.

Database Interactions

  • Mandate column comments. Every database table column must feature a clear comment explaining its function, particularly for flags and legacy status fields. This acts as self-updating documentation that is instantly visible to any developer querying the database.
  • Abolish overloaded, multi-meaning columns. A column must represent exactly one piece of information. Overloading a status column to mean different things depending on the value of a sibling column is a severe architectural flaw that complicates queries and breeds subtle bugs.
  • Optimize index coverage. Every query path executed regularly must be validated for index efficiency using EXPLAIN. Design composite indexes based on the leftmost prefix rule. Avoid adding indexes blindly, as each index incurs a write-performance penalty.
  • Explicitly define columns in queries; avoid SELECT *. Only request columns that are strictly necessary for the operation. Using SELECT * wastes network throughput, breaks application code when database schemas change, and prevents query planners from leveraging covering indexes.
  • Strictly forbid remote network calls within database transactions. Keep your transactions as short and fast as possible. Never make HTTP requests, publish messages to external brokers, or invoke third-party services while a database transaction is active. Network latency is unpredictable; holding a transaction open while waiting on a remote endpoint locks database rows, frequently causing cascading thread pool exhaustion.

Controllers

  • Forbid static controller methods. Controller methods must always be instance methods. Static methods inhibit test-double substitution, prevent clean dependency injection, and introduce tight, invisible coupling.
  • Banish business logic from controllers. A controller's single responsibility is to receive an incoming HTTP request, validate its structure, delegate orchestration to an application service, and return an HTTP response. If a controller method exceeds 20 lines, it is doing too much and must be refactored.
// Correct: Thin, compliant controller
class OrderController
{
    public function store(Request $request, OrderService $orderService): Response
    {
        $data = $request->validate([
            'product_id' => 'required|integer',
            'quantity'   => 'required|integer|min:1',
        ]);

        $order = $orderService->createOrder($data);

        return new JsonResponse(['order_id' => $order->getId()], 201);
    }
}

Session Management

  • Limit session data to context identifiers. Sessions must only store minimal context required to authenticate and authorize a user: user ID, active session tokens, CSRF tokens, and localization preferences. Never store domain objects, large arrays, or business payloads in sessions; use dedicated cache stores instead.
  • Regenerate session IDs upon authentication transitions. Protect against session fixation attacks by immediately regenerating the session identifier whenever a user's privilege level changes (such as logging in or out).

API Design

  • Mandate up-to-date documentation. Every API endpoint must have clear documentation detailing request payloads, response schemas, and specific error codes. An undocumented API is a non-functional API.
  • Preserve backward compatibility. Once an API is published, do not introduce breaking changes. Never drop response fields, change data types, or modify parameter constraints. If breaking changes are unavoidable, expose them via a new API version (e.g., /v2/).
  • Enforce idempotency boundaries. State-modifying operations should be designed to be idempotent where feasible. While PUT and DELETE are naturally idempotent, POST operations must be protected using unique idempotency keys in request headers (e.g., to prevent double-charging on payment endpoints).
  • Standardize response envelopes. Maintain a uniform payload structure across all endpoints. Success and failure structures should be identical, differing only in the metadata, payload, and HTTP status code.
// Success Envelope
{
    "code": 0,
    "message": "success",
    "data": {
        "order_id": 12345,
        "status": "created"
    }
}

// Error Envelope
{
    "code": 20001,
    "message": "Insufficient balance",
    "data": null
}

Other Core Rules

  • Abolish duplicate code. Copy-pasting code is a form of technical debt. Extract shared logic into reusable, testable helper functions or utility classes. Adherence to the DRY (Don't Repeat Yourself) principle is a non-negotiable requirement.
  • Cap method length at 120 lines. A method exceeding 120 lines is overloaded with multiple responsibilities. Decompose it into smaller, cohesive methods that each do one thing exceptionally well. Shorter methods are significantly easier to inspect, test, and maintain.
  • Strictly separate commands from queries. Any method whose name implies data retrieval (e.g., getUser, findOrders, calculateTotal) must not introduce side effects or modify state. Keep query methods pure and deterministic. If a method must perform both operations, its name must clearly reflect the mutation, or preferably, be decomposed.
  • Implement Fail-Fast validation. Assert input preconditions immediately at the start of a method block. If an argument is malformed, throw a specific exception immediately. This prevents invalid data from propagating deep into the call stack, isolating failures early when they are cheapest to handle.

Enforcement Mechanisms

Standards without automated enforcement are nothing more than polite suggestions. To ensure these rules remain unbreakable:

  • Automate formatting checks: Integrate PHP_CodeSniffer with strict PSR-12 rule mappings into your continuous integration (CI) pipeline. Block any merge requests that fail formatting checks.
  • Leverage static analysis: Mandate tools like PHPStan or Psalm at level 5 or higher. Static analysis proactively catches type mismatches, undefined references, and logic bugs long before code reaches production.
  • Standardize code reviews: Require at least one peer approval before merging. Reviewers must inspect incoming code not only for immediate correctness but also for alignment with these design standards.
  • Lead by example: Senior engineers must champion these conventions. If leadership cuts corners and bypasses standards, the conventions will quickly be ignored by the rest of the team.

Summary

Adopting engineering standards is a long-term investment. It demands immediate setup time, rigorous daily discipline, and the courage to block substandard code. However, the return on investment is massive: highly readable, uniform, and self-documenting codebases, frictionless onboarding for new developers, and an engineering culture where bugs are isolated and eliminated in staging rather than production.

The rules outlined here represent industry-standard best practices, refined by decades of combined development experience. Adapt them to your team's specific requirements, automate their enforcement, and hold your codebase to a higher standard. Your future self — and your production stability — will thank you.
