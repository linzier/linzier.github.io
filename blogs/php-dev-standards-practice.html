PHP Development Standards: In Practice

2020-04-26 | PHP

Coding standards are not about aesthetics. They are about reducing cognitive load. When every file in a codebase follows the same conventions, developers spend less time parsing format and more time understanding logic. Standards are a tax on discipline that pays dividends in maintainability. Here is a practical set of PHP development standards, battle-tested across multiple projects.

Part 1: Code Format

The formatting rules below are based on PSR-1, PSR-2, and PSR-12, with some project-specific adjustments. The goal is consistency: any developer should be able to open any file and immediately feel at home.

Files

  • Encoding: UTF-8 without BOM. The BOM (Byte Order Mark) causes subtle issues with headers, session handling, and output buffering. There is no reason to use it.
  • Closing tag: Omit the closing ?> tag for files that contain only PHP code. This prevents accidental whitespace from being sent as output, which can cause “headers already sent” errors.
  • One file, one class: Each class should live in its own file. The filename should match the class name. This is not just a convention — it is required for PSR-4 autoloading to work correctly.

Lines

  • Maximum line length: 80 characters. Lines longer than 80 characters should be split into multiple lines. This is not about fitting on an 80-column terminal — it is about readability during code review, side-by-side diffs, and printing.
  • No trailing whitespace: Trailing spaces are invisible noise. They cause meaningless diff entries and indicate sloppiness. Configure your editor to strip trailing whitespace on save.
  • Line endings: Use LF (\n) consistently. Do not mix LF and CRLF.

Indentation

  • 4 spaces. Not tabs. Not 2 spaces. Four spaces. Tabs render differently in different editors, causing visual inconsistency. Spaces are universal.

Naming Conventions

  • Classes: CamelCase (upper camel case / Pascal case). Examples: UserController, OrderRepository, PaymentGateway.
  • Methods: camelCase (lower camel case). Examples: getUserById, calculateTotal, isValid.
  • Constants: UPPER_SNAKE_CASE. Examples: MAX_RETRY_COUNT, DEFAULT_PAGE_SIZE, STATUS_ACTIVE.
  • Variables: $camelCase. Descriptive names. $user is fine. $u is not. $data is too vague — use $userData, $orderData, or something specific.
  • Boolean variables and methods: Prefix with is, has, can, should. Examples: $isActive, hasPermission(), canExecute(). This makes the intent immediately clear at the call site.

Control Structures

  • One space after the control structure keyword (if, for, while), one space before the opening brace.
  • Opening brace on the same line as the control structure keyword.
  • Closing brace on its own line, aligned with the control structure keyword.
  • Always use braces, even for single-line bodies. if ($x) doSomething(); is forbidden. It is a maintenance hazard — someone will add a second line and forget the braces.
  • elseif is one word, not else if.
// Correct
if ($condition) {
    doSomething();
} elseif ($otherCondition) {
    doSomethingElse();
} else {
    doDefault();
}

// Forbidden
if ($condition) doSomething();
if ($condition)
    doSomething();

Braces and Spacing

  • Function and method declarations: opening brace on the next line (following the PSR-2/12 style for class methods).
  • Function calls: no space between the function name and the opening parenthesis.
  • Binary operators: one space on each side ($a + $b, not $a+$b).
  • Unary operators: no space between the operator and the operand (!$flag, not ! $flag).
  • Commas: followed by a space (foo($a, $b, $c)).
  • Array declarations: use short syntax [], not array().

Closures (Anonymous Functions)

  • Add a space after the function keyword and before the use keyword.
  • Opening brace on the same line.
  • The use clause imports variables from the parent scope.
$greet = function ($name) use ($defaultGreeting) {
    return $defaultGreeting . ', ' . $name;
};

Comments

  • Doc comments: Use /** ... */ for classes, methods, and properties. Include @param, @return, and @throws annotations.
  • Inline comments: Use // for single-line comments. Place the comment on the line above the code it describes, not on the same line (unless it is a very short note).
  • Comment in English. Code comments should be written in English, even if the team primarily speaks another language. This ensures that non-native speakers and future tooling can process them.
  • Comment the “why,” not the “what.” The code tells you what it does. The comment should explain why it does it that way. If you find yourself writing a comment that restates the code, rewrite the code to be clearer instead.

Part 2: Program Design

Code format is the surface. Program design is the substance. These rules govern how we structure logic, handle errors, manage state, and build APIs.

Exceptions

  • Throw exceptions to signal errors. Do not return error codes, error strings, or false to indicate failure. Exceptions force the caller to acknowledge the error (either catch it or let it propagate). Return values can be silently ignored.
  • Exception: controller layer. At the controller (or HTTP handler) level, catch exceptions and convert them to appropriate HTTP responses. The controller is the boundary between the application’s internal error model and the external HTTP error model.
  • Use specific exception types. Do not throw generic \Exception. Create domain-specific exceptions: UserNotFoundException, InsufficientBalanceException, PaymentGatewayTimeoutException. This allows callers to catch and handle specific error conditions.
  • Include context in exceptions. An exception message should include enough information to diagnose the problem without reading the code. Include the relevant entity ID, the operation that failed, and any relevant state.

Status Codes and Error Codes

  • Define error codes as constants. Every distinct error condition should have a unique, named constant. Never use magic numbers or strings.
  • One code per error. Each error condition must have a unique code. Do not reuse the same code for different errors. This makes debugging and monitoring impossible.
class ErrorCode
{
    public const USER_NOT_FOUND       = 10001;
    public const USER_ALREADY_EXISTS  = 10002;
    public const INVALID_EMAIL_FORMAT = 10003;
    public const INSUFFICIENT_BALANCE = 20001;
    public const PAYMENT_TIMEOUT      = 30001;
}

Logging

  • Follow PSR-3. Use the PSR-3 logger interface. This ensures that your logging code is decoupled from the logging implementation (Monolog, etc.).
  • Application layer preferred. Log at the application/service layer, not at the infrastructure layer. The database layer should not log every query. The service layer should log significant business operations.
  • Log levels matter. Use ERROR for things that need immediate attention. Use WARNING for things that are unexpected but recoverable. Use INFO for significant business events. Use DEBUG for development-time diagnostics. Do not log everything at INFO level.
  • Structured logging. Use context arrays, not string interpolation. $logger->error('Payment failed', ['orderId' => $id, 'error' => $e->getMessage()]) is better than $logger->error("Payment failed for order $id: " . $e->getMessage()).

Caching

  • Follow PSR-16 (Simple Cache). Use the PSR-16 interface for cache operations. This decouples your code from the cache backend (Redis, Memcached, file, etc.).
  • Always set a TTL. Every cache entry must have a time-to-live. Cache entries without TTL accumulate indefinitely, consuming memory and serving stale data. Choose a TTL appropriate to the data’s volatility: 5 minutes for frequently changing data, 1 hour for moderately stable data, 24 hours for rarely changing data.
  • Cache invalidation strategy. Define how cache entries are invalidated when the underlying data changes. Options: TTL-based expiry, event-driven invalidation (delete cache on write), or versioned keys.

Database

  • Field comments. Every database column must have a comment explaining its purpose, especially for non-obvious fields. This is documentation that lives with the data and is visible in any database client.
  • No multi-meaning fields. A field should represent exactly one thing. A status field that means different things depending on the value of another field is a design flaw. It makes queries confusing and bugs likely.
  • Proper indexes. Every query that runs frequently should be analyzed for index usage. Use EXPLAIN to verify. Composite indexes should follow the leftmost prefix rule. Do not add indexes blindly — each index has a write cost.
  • No SELECT *. Always specify the columns you need. SELECT * wastes network bandwidth, breaks when columns are added or removed, and prevents covering index optimizations.
  • No remote calls in transactions. A database transaction should be as short as possible. Never make HTTP calls, send messages to a queue, or call external services while a transaction is open. Remote calls are slow and unreliable — if they timeout, your transaction holds locks for an extended period, potentially causing cascading failures.

Controllers

  • No static methods. Controller methods should be instance methods. Static methods make testing difficult, prevent dependency injection, and create hidden coupling.
  • No business logic. The controller’s job is to receive the HTTP request, delegate to a service/handler, and return the HTTP response. Business logic belongs in the service layer. If your controller method is longer than 20 lines, it is doing too much.
// Correct: thin controller
class OrderController
{
    public function store(Request $request, OrderService $orderService): Response
    {
        $data = $request->validate([
            'product_id' => 'required|integer',
            'quantity'   => 'required|integer|min:1',
        ]);

        $order = $orderService->createOrder($data);

        return new JsonResponse(['order_id' => $order->getId()], 201);
    }
}

Session

  • Only store session context. The session should contain only the information needed to identify the user and their session state: user ID, authentication token, CSRF token, locale preference. Do not store business data in the session. Do not store large objects. Do not use the session as a convenience cache.
  • Regenerate session ID after authentication. Prevent session fixation attacks by regenerating the session ID when the user’s authentication state changes.

API Design

  • Documentation. Every API endpoint must have documentation: request parameters, response format, error codes, and example requests/responses. Undocumented APIs are unusable APIs.
  • Backward compatibility. Once an API is published, do not break it. Do not remove fields from responses. Do not change field types. Do not change the meaning of parameters. If you need to make breaking changes, create a new version (/v2/).
  • Idempotency. Operations that modify state should be idempotent where possible. PUT and DELETE are naturally idempotent. For POST operations that should not be duplicated (e.g., payment processing), require an idempotency key in the request header.
  • Consistent response structure. All API responses should follow the same envelope format. Success and error responses should be structurally identical, differing only in the status code and error details.
// Success response
{
    "code": 0,
    "message": "success",
    "data": {
        "order_id": 12345,
        "status": "created"
    }
}

// Error response
{
    "code": 20001,
    "message": "Insufficient balance",
    "data": null
}

Other Rules

  • No code duplication. If you copy-paste code, you have created a maintenance burden. Extract the common logic into a function or method. The DRY principle (Don’t Repeat Yourself) is not optional.
  • Maximum 120 lines per method. If a method exceeds 120 lines, it is doing too much. Break it into smaller methods. Each method should do one thing and do it well. This is not just about readability — long methods are harder to test, harder to debug, and more likely to contain bugs.
  • No side effects in query methods. A method whose name suggests it retrieves data (getUser, findOrders, calculateTotal) must not modify state. Query methods should be pure: same input, same output, no side effects. If a method both queries and modifies, its name should reflect both actions, or better yet, it should be split into two methods.
  • Fail fast. Validate inputs at the beginning of a method. If a parameter is invalid, throw an exception immediately. Do not let invalid data propagate deep into the call stack before failing. Early failure is cheap failure.

Enforcement

Standards without enforcement are just suggestions. Here is how to make them stick:

  • Automated tools. Use PHP_CodeSniffer with a PSR-12 ruleset. Integrate it into your CI pipeline. Code that does not pass the linter does not get merged. No exceptions.
  • Static analysis. Use PHPStan or Psalm at a reasonable level (level 5 or higher). These tools catch type errors, undefined variables, and logic bugs that a linter cannot.
  • Code review. Every pull request should be reviewed by at least one other developer. Reviewers should check not just for correctness, but for adherence to these standards.
  • Lead by example. Senior developers must follow the standards themselves. If the team lead writes code that violates the standards, the standards become meaningless.

Summary

Development standards are an investment. They cost time to establish, discipline to maintain, and courage to enforce. But the return is substantial: codebases that are readable, maintainable, and debuggable. New team members who can be productive in days, not weeks. Bugs that are caught before they reach production.

The standards described here are not unique to any team. They are distilled from PSR-1, PSR-2, PSR-3, PSR-12, and decades of collective industry experience. Adopt them, adapt them to your context, and enforce them consistently. Your future self — and your future teammates — will thank you.
