Technical Team Development & Release Standards

2020-04-23 | Process

Iteration Cycle

Our team operates on a monthly development cycle, divided into two two-week sprints:

  • S1 — the first two weeks of the month.
  • S2 — the remaining two weeks of the month.

For each sprint, the team commits to a defined scope of requirements. At the end of each sprint, we conduct a demo and a retrospective to assess deliverables, celebrate achievements, and identify areas for improvement.

Requirements Management

Product vs. Technical Requirements

Requirements generally fall into two categories:

  • Product requirements — features and user experience changes driven by business needs, defined by the Product Manager.
  • Technical requirements — infrastructure improvements, refactoring, performance optimization, and tech debt reduction, initiated by the engineering team.

Both types undergo the same review and planning process. Technical requirements are just as critical as product features and must be allocated dedicated capacity within each sprint.

Planned vs. Ad-hoc Requirements

  • Planned requirements are those identified during sprint planning and committed to at the start of the sprint.
  • Ad-hoc requirements are urgent requests that arise mid-sprint. These must be evaluated for priority and impact before they can be accepted. If an ad-hoc requirement is approved, an existing task of equivalent effort must be deprioritized to maintain sprint balance.

Review Process

All requirements must go through a formal review process before development begins:

  1. The Product Manager drafts the requirements document (PRD).
  2. The Tech Lead reviews the technical feasibility and estimates the required effort.
  3. The team discusses and refines the requirement during the sprint planning meeting.
  4. Acceptance criteria are clearly defined and agreed upon by all stakeholders.

Development Phase

Branching Strategy

Each requirement is developed in its own feature branch, created from the latest master. Branch naming follows this convention:

feature-<developer>-<description>

Developers should merge the latest master branch into their feature branches daily to catch integration issues early.

Daily Standups

Each day, the team holds a brief standup meeting (15 minutes max) where each member answers three questions:

  1. What did I accomplish yesterday?
  2. What do I plan to work on today?
  3. Are there any blockers in my way?

The standup is not a status report for management; it is a synchronization mechanism for the development team.

Testing Phase

Submitting for Testing

Once development is complete, the developer hands off the feature to the QA team, providing the following details:

  • Requirement ID and description
  • Branch name and version number
  • Scope of impact (affected modules/components)
  • Testing recommendations and key scenarios to verify
  • Known issues or limitations
  • Database migration scripts (if applicable)
  • Configuration changes (if applicable)

Bug Resolution SLAs

During testing, bugs are categorized by severity with the following committed turnaround times:

  • Critical (P0) — Blocks testing or causes data loss: Fix within 4 hours.
  • High (P1) — Major functionality broken: Fix within 1 business day.
  • Medium (P2) — Minor functionality issue: Fix within 2 business days.
  • Low (P3) — Cosmetic or trivial issue: Fix before release or defer to the next sprint.

Pre-release Phase

Release Branch

When a sprint is ready for release, a release branch is cut from the latest master:

release-YYYYMMDD.NN

All QA-approved features are merged into this release branch. The release branch is then deployed to the staging (pre-production) environment for final verification.

Deployment Notifications

Before deploying to production, the release manager sends a deployment notification to all stakeholders, containing:

  • A list of features and requirements included in the release
  • The deployment window
  • Expected downtime (if any)
  • Database migration steps
  • Configuration changes
  • A rollback plan
  • Post-deployment verification steps

Production Release

Approval Process

Production releases require formal sign-off:

  1. QA signs off, confirming all test cases have passed and no critical bugs remain open.
  2. The Tech Lead confirms that code reviews are complete and the architecture is sound.
  3. The Product Manager confirms that the delivered features align with the original requirements.
  4. The Operations/SRE team confirms the deployment runbook is ready.

Risk Assessment

Before every production release, the team conducts a risk assessment:

  • What is the blast radius if the deployment fails?
  • Are there external dependencies on other system releases?
  • Does this coincide with a peak traffic window? Should we defer the release?
  • Are there database schema migrations that could lock production tables?

Rollback Plan

Every release must be accompanied by a rollback plan that specifies:

  • The exact steps required to revert to the previous stable version.
  • How to handle database migrations (e.g., forward-only or fully reversible).
  • The engineer responsible for executing the rollback.
  • The specific triggers for a rollback (e.g., error rates exceeding a threshold).
  • The estimated time to complete the rollback.
A release without a rollback plan is not a release; it is a gamble.

Summary

Adhering to a disciplined development and release workflow is not about enforcing bureaucracy; it is about mitigating uncertainty and building trust. When expectations are clear, the team can move faster with fewer surprises. The core principles are:

  • Establishing clear requirements before any coding begins.
  • Using isolated feature branches for all development.
  • A formal handoff process among development, QA, and operations.
  • Conducting risk assessments and defining rollback plans for every production deployment.
