Technical Team Development & Release Standards

2020-04-23 | Process

Iteration Cycle

Our team operates on a monthly iteration cycle. Each month is divided into two sprints:

  • S1 — the first two weeks of the month.
  • S2 — the last two weeks of the month.

Each sprint has a defined scope of requirements that the team commits to delivering. At the end of each sprint, there is a demo and retrospective to assess what was accomplished and identify areas for improvement.

Requirements Management

Product vs Technical Requirements

Requirements come in two flavors:

  • Product requirements — features and changes driven by business needs, defined by the product manager.
  • Technical requirements — infrastructure improvements, refactoring, performance optimization, and tech debt reduction, initiated by the engineering team.

Both types go through the same review and planning process. Technical requirements are just as important as product requirements and must be allocated dedicated capacity in each sprint.

Planned vs Ad-hoc Requirements

  • Planned requirements are those identified during sprint planning and committed to at the beginning of the sprint.
  • Ad-hoc requirements are urgent requests that arise mid-sprint. These must be evaluated for priority and impact before being accepted. If an ad-hoc requirement is accepted, something else must be deprioritized to maintain the sprint's balance.

Review Process

All requirements must go through a formal review process before development begins:

  1. Product manager writes the requirement document.
  2. Technical lead reviews feasibility and estimates effort.
  3. The team discusses the requirement in a planning meeting.
  4. Acceptance criteria are clearly defined and agreed upon.

Development Phase

Branch Strategy

Each requirement gets its own feature branch, branched from the latest master. Branch naming follows the convention:

feature-<developer>-<description>

Developers should merge the latest master into their feature branch daily to catch integration issues early.

Daily Standups

Each day, the team holds a brief standup meeting (15 minutes max) where each member answers three questions:

  1. What did I accomplish yesterday?
  2. What do I plan to work on today?
  3. Are there any blockers in my way?

The standup is not a status report to management; it is a synchronization mechanism for the team.

Testing Phase

Submission for Testing

When development is complete, the developer submits the feature for testing by sending an email to the QA team with the following information:

  • Requirement ID and description
  • Branch name and version number
  • Impact scope (which modules are affected)
  • Test suggestions and key scenarios to verify
  • Known issues or limitations
  • Database migration scripts (if any)
  • Configuration changes (if any)

Bug Fix SLA

Once testing begins, bugs are categorized by severity, and the development team commits to the following response times:

  • Critical (P0) — blocks testing or causes data loss: fix within 4 hours.
  • High (P1) — major functionality broken: fix within 1 business day.
  • Medium (P2) — minor functionality issue: fix within 2 business days.
  • Low (P3) — cosmetic or trivial: fix before release or deferred to next sprint.

Pre-release Phase

Release Branch

When the sprint is ready for release, a release branch is created from the latest master:

release-YYYYMMDD.NN

All features that have passed testing are merged into this release branch. The release branch is then deployed to the pre-production (staging) environment for final verification.

Deployment Notification

Before deploying to production, the release manager sends a deployment email to all stakeholders containing:

  • List of features/requirements included in this release
  • Deployment time window
  • Expected downtime (if any)
  • Database migration steps
  • Configuration changes
  • Rollback plan
  • Verification steps after deployment

Production Release

Approval Process

Production releases require formal approval:

  1. QA signs off that all test cases pass and no critical bugs remain open.
  2. Technical lead confirms the code review is complete and the architecture is sound.
  3. Product manager confirms the delivered features match the requirements.
  4. Operations team confirms the deployment runbook is ready.

Risk Assessment

Before every production release, the team conducts a risk assessment:

  • What is the blast radius if something goes wrong?
  • Are there dependencies on other systems being released?
  • Is this a peak traffic period? Should we defer the release?
  • Are there database schema changes that could lock tables?

Rollback Plan

Every release must have a rollback plan. The rollback plan should specify:

  • The exact steps to revert to the previous version.
  • How to handle database migrations (forward-only or reversible?).
  • Who is responsible for executing the rollback.
  • The criteria that trigger a rollback (e.g., error rate above threshold).
  • Estimated time to complete the rollback.
A release without a rollback plan is not a release; it is a gamble.

Summary

Following a disciplined development and release process is not about bureaucracy; it is about reducing uncertainty and building trust. When everyone knows what to expect, the team can move faster with fewer surprises. The key principles are:

  • Clear requirements before coding begins.
  • Isolated branches for each feature.
  • Formal handoff between development, testing, and operations.
  • Risk assessment and rollback plans for every production change.
