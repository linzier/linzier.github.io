Why Skip Lists When We Have Red-Black Trees?

2023-07-10 | Data Structures

Picking up where we left off — in the previous article, How Red-Black Trees Came to Be, we discussed how red-black trees (which are essentially an implementation of 2-3 trees or 2-3-4 trees) maintain the balance of binary search trees. From the implementation perspective, although red-black trees simplify things considerably compared to 2-3 trees, they are still quite complex.

Is there a simpler approach?

Born from the Idea of Binary Search

In an earlier article, The Essence of Binary Search Trees, we derived binary search trees by turning the binary search on sorted arrays into a linked structure. This time, let's start from the same place — binary search on a sorted array — and see if we can invent something new.

The difference this time: we first convert the sorted array into a linked list.

As shown in the figure, we now have a sorted linked list. Consider how we would search for the element 40.

The simplest approach is to traverse from the head one node at a time, with time complexity O(n) — clearly not what we want.

Our initial thought: can we perform binary search on this linked list?

With an array, we can jump directly to the middle element (15) via address offset, discover that 40 is greater than 15, and then continue the binary search on the right half.

The problem with a linked list is that there is no way to jump directly to an arbitrary position — no address offset trick available.

But we are not ready to give up. Is there some clever trick to simulate binary search on a linked list?

Since a linked list only allows traversal via pointers, could we add extra pointers between key nodes — the head, the tail, and the middle elements that binary search would touch — to enable fast jumps?

We build an additional linked list (1 → 15 → 60), where each node also has a "down" pointer to the corresponding node in the layer below.

What does this buy us?

Let's see how we would search for 40 now.

We first traverse the upper (second-level) linked list. In just two steps, we reach element 15. We see that 40 lies between 15 and 60 (15's next element), so we follow 15's "down" pointer to the first-level linked list and continue searching from there.

Unlike a plain linear traversal, by adding one layer of "index" linked list, we can "jump" directly to the middle element, just like binary search does. Search efficiency doubles immediately.

Can we optimize further?

In the diagram above, the search after 15 is still linear. We can apply the same trick again — build index lists for the sub-lists between 1–15 and 15–60:

It looks a bit complicated at first glance, but it is really just another level of binary search simulation.

Let's look at it from the top layer down.

The third layer performs the first binary split, with 15 as the pivot. Depending on the comparison, we go to either the 1–15 range or the 15–60 range.

The second layer performs the second binary split within the chosen range, narrowing down to a finer-grained interval.

So if we search from the topmost index layer downward, we are effectively simulating repeated binary searches on a sorted array.

Brilliant!

Let's trace the search path for element 40 after adding two layers of indexes:

Compared to a single layer, the search path is much shorter.

Unlike a plain linked list, this structure uses index layers to "skip" over nodes for faster searching. Hence the delightfully self-explanatory name: skip list.

Since a skip list is essentially a simulation of binary search, its search time complexity is O(log n), same as binary search.

Data Structure

A skip list node (except those in the bottom layer) needs not only a pointer to its successor (and predecessor, if doubly linked) but also a pointer to the corresponding node in the layer below. So we might initially define the node structure as:

class Node {
    key: number
    val: unknown
    next: Node | null
    down: Node | null
    public constructor(key: number, val: unknown) { }
}

Let's analyze whether this design has any issues.

First, a note: using index lists to speed up search is a classic space-for-time tradeoff.

However, we create a separate object for the same element (say, 15) at every layer. Isn't that wasteful?

All three nodes for element 15 share the same key and val. The main difference lies in the next pointers — each layer has a different successor. Upper-layer nodes always "descend" layer by layer.

So we can try merging the per-layer nodes for the same element into one. We combine next and down into a single nexts pointer array, where nexts[i] represents the node's successor at layer i+1.

As shown in the diagram, we made four changes:

  1. Merged same-key nodes across all layers into a single node;
  2. Introduced the nexts pointer array, where node.nexts[i] is node's successor at layer i+1;
  3. Added a sentinel head node (representing no actual element) for coding convenience;
  4. No longer create index entries for the tail node;

Searching for an Element

Let's see how to find node 40. Every search starts from head at the topmost layer and works down to layer 1:

  1. Take head.nexts[top layer] — it's 15, which is less than 40, so move to node 15;
  2. Take node15.nexts[top layer] — it's null, meaning we can't go further right at this layer, so drop down to the second layer;
  3. Take node15.nexts[second layer] — it's 30, less than 40, so move to node 30;
  4. Take node30.nexts[second layer] — it's null, so drop down to the first layer;
  5. Take node30.nexts[first layer] — it's 40. Found! Return and done.

Ridiculously simple, right?

Number of Index Layers

Before discussing insertion, let's think about a question: how many layers should a given element have?

Skip lists use a simple, brute-force, yet effective approach: probability.

The idea is this: we stipulate that the number of elements at layer n is 1/N of the count at layer n-1. In other words, each element has a 1/N probability of gaining one more index layer above.

With N=4 as an example:

  • 3/4 probability of having no index at all (only the bottom layer)
  • 1/4 probability of 1 index layer
  • 1/16 probability of 2 index layers
  • 1/64 probability of 3 index layers

The resulting data structure is essentially an N-ary tree.

Inserting an Element

The average time complexity of insertion is O(log n). The key is finding the predecessor node at each layer.

Deleting an Element

Deletion in a skip list is essentially the inverse of insertion: remove the node from every layer.

Remarkably, the structure after deletion is identical to the structure before insertion — such dynamic stability is truly admirable.

The Source of Simplicity

Compare the insertion and deletion implementations of red-black trees with those of skip lists, and you will be struck by how simple skip lists are.

Skip lists adopt a simple, brute-force, yet equally effective probabilistic approach. When inserting an element, we determine the number of index layers through a probability calculation. Updating the indexes only affects the predecessor nodes of the new element at each layer — a very localized impact, making the update process extraordinarily simple.

In short, the probabilistic nature of this data structure is the source of its simplicity.

Summary

  1. Derived the multi-level index approach for linked structures from the binary search idea on sorted arrays;
  2. Used probability to determine each element's index layer count, ensuring implementation simplicity while maintaining theoretical correctness;
  3. The key to insertion and deletion is finding the predecessor node at each layer;
  4. Insertion and deletion are perfect inverses of each other, demonstrating excellent dynamic stability;
  5. Skip lists and red-black trees offer the same level of time complexity, but skip lists are simpler to implement and more intuitive for range queries;
