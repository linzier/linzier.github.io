Why Skip Lists When We Have Red-Black Trees?

2023-07-10 | Data Structures

In our previous article, How Red-Black Trees Came to Be, we explored how red-black trees (an elegant encoding of 2-3 or 2-3-4 trees) maintain binary search tree balance. Red-black trees are a substantial simplification over raw 2-3 trees, yet implementing them correctly remains notoriously complex and error-prone.

Is there a simpler path to the same efficiency?

Born from the Core of Binary Search

In The Essence of Binary Search Trees, we derived BSTs by converting a binary search on a sorted array into a pointer-linked structure. Now let's start from the same foundation — binary search on sorted data — and see if we can invent a different, equally elegant structure.

The twist: we begin by representing sorted data as a singly linked list.

As shown in the figure, we now have a sorted linked list. Suppose we want to search for the element 40.

The naive approach is to traverse from the head, one element at a time. This yields O(n) time complexity — far too slow.

Can we perform binary search on a linked list?

With an array, we jump directly to the middle element (15) via address offset, determine that 40 > 15, and recurse on the right half.

A linked list cannot jump to an arbitrary index. No constant-time offset trick is available.

But what if we augmented the list with extra pointers to simulate binary search?

Since a linked list restricts us to sequential traversal, what if we added a sparse layer of pointers at key nodes — head, tail, midpoint — to bypass large chunks of the list?

We construct an auxiliary index list (1 → 15 → 60), where each index node also holds a down pointer to its counterpart in the original list below.

What does this buy us? Let's re-evaluate the search for element 40.

We start on the upper index list. In two hops, we reach element 15. Since 40 lies between 15 and 60, we follow the down pointer from 15 to descend into the first-level list and resume the search.

By introducing a single index layer, we leap directly to the dataset's midpoint — mimicking the first step of binary search. Search efficiency doubles.

Can we push further?

After descending past 15, the search is still linear. We can recursively apply the indexing strategy — building additional layers for the sub-lists between 1–15 and 15–60:

The diagram looks complex, but it is simply a multi-tiered simulation of a binary search tree.

Trace it top-down:

The third layer performs the first binary partition on pivot 15, routing the search to either the 1–15 or 15–60 range.

The second layer performs the next partition within that range, narrowing to a finer interval.

Starting from the topmost layer and dropping down as needed, we execute binary search over a linked list.

Here is the search path for element 40 with two index layers:

Compared to a flat list, the search path is drastically shorter.

This structure leverages index layers to "skip" over large blocks of nodes. Hence the name: skip list.

Because a skip list mirrors binary search structurally, it achieves O(log n) search — matching balanced binary trees.

The Node Architecture

A skip list node (except in the bottom layer) must store a pointer to its successor and a pointer to the matching node in the layer below. A naive TypeScript implementation:

class Node {
    key: number
    val: unknown
    next: Node | null
    down: Node | null
    public constructor(key: number, val: unknown) { }
}

Does this design have structural drawbacks?

First, an observation: using index lists to accelerate search is a textbook space-for-time trade-off.

However, instantiating a new node object for the same element (e.g., 15) at every layer is wasteful. All nodes for element 15 share the same key and value. The only difference is their next pointers — each layer points to a different successor.

We can optimize by merging multi-layer nodes into a single object. We replace the individual next and down pointers with a forward pointer array nexts, where nexts[i] stores the successor at layer i+1.

This optimization introduces four changes:

  1. Multi-layer representation of an element collapses into a single node.
  2. A nexts pointer array, where node.nexts[i] references the successor at layer i+1.
  3. A sentinel head node (no key or value) to simplify boundary conditions.
  4. No index array for the tail node, saving memory.

Searching for an Element

Trace the search for node 40. Every search begins at sentinel head at the topmost layer and descends to layer 1:

  1. head.nexts[top] points to 15. Since 15 < 40, advance to node 15.
  2. node15.nexts[top] is null — cannot proceed right at this level. Drop to the second layer.
  3. node15.nexts[second] points to 30. Since 30 < 40, advance to node 30.
  4. node30.nexts[second] is null. Drop to the first layer.
  5. node30.nexts[first] points to 40. Target found.

This traversal is incredibly simple and elegant.

Determining Index Heights

Before insertion, we must answer a key question: how many index layers should a newly inserted element span?

Rather than complex rebalancing, skip lists use probability.

The principle: nodes at layer n are roughly 1/N of the nodes at layer n-1. Every inserted node has a 1/N probability of promotion to the layer above.

With N=4:

  • 3/4 probability: node exists only at the base layer.
  • 1/4 probability: promoted to layer 2.
  • 1/16 probability: reaches layer 3.
  • 1/64 probability: reaches layer 4, and so on.

This probabilistic model shapes the skip list into an N-ary tree structure on average.

Inserting an Element

Insertion runs in O(log n) average time. The core mechanic: traverse the list to locate and record the predecessor at each layer, then splice the new node into the pointer arrays.

Deleting an Element

Deletion is the clean inverse of insertion: locate the predecessors at each layer and update their pointers to bypass the target node.

Deleting and re-inserting the same node restores the exact same structural properties — a testament to the skip list's dynamic stability.

The Source of Simplicity

Compare insertion and deletion in a red-black tree with those in a skip list. The contrast is stark: the skip list is vastly easier to write, understand, and debug.

A red-black tree relies on complex rotations, color-flipping, and conditional branches to maintain strict balance. A skip list relies on local, probabilistic choices. When inserting, we calculate height with a random number generator. Splicing affects only the immediate predecessor at each level — a localized mutation that keeps the code clean.

Embracing probability is what makes this data structure so simple.

Summary

  1. Skip list multi-level index architecture derives from adapting binary search to a pointer-linked structure.
  2. Probability determines node heights, matching balanced tree performance while dramatically simplifying implementation.
  3. Insertion and deletion both hinge on tracking and updating predecessors at each level.
  4. Insertion and deletion are logical inverses, providing natural dynamic balance.
  5. Skip lists and red-black trees offer identical time complexities, but skip lists are significantly easier to implement and superior for range queries.
