Why Is Programming So Hard?

2022-04-21 | Philosophy | 5,534 reads

A "Simple" Example

Let's start with a scenario that sounds trivially simple. You're at a gas station, and you pay with a prepaid card. The flow should be straightforward:

  1. Scan the card.
  2. Create an order.
  3. Deduct the amount from the card.
  4. Return success.

Four steps. What could go wrong?

Plenty, as it turns out. The happy path is easy. It's everything else that makes programming hard.

The Timeout at Step 3

You call the card deduction service. And you get... a timeout. No response. You don't know if the deduction succeeded or failed.

What do you do?

Option A: Return Failure

The simplest approach: tell the user the payment failed. But wait — what if the deduction actually succeeded on the card system's side? The network response was lost, but the money was deducted. Now the user has been charged but didn't get their gas.

You can't just return failure. The absence of a response is not a failure response.

Option B: Query the Result

OK, so you query the card system to check the transaction status. But the query also times out. Now you're in a worse position — you don't even know if your query is reliable.

And even if the query succeeds, the deduction might still be "in progress" on the card system's side. The card system might process things asynchronously. So the status might be "processing" — which tells you nothing about the final outcome.

Option C: Cancel the Deduction

Fine, let's just cancel the deduction to be safe. If it succeeded, the cancel will refund it. If it didn't succeed, the cancel will be a no-op.

But here's the catch: the original deduction might still be in flight. Your cancel request might arrive before the deduction completes. The card system processes the cancel first (no-op, since no deduction exists yet), then processes the deduction (which succeeds). Now the user is charged, and you thought you cancelled it.

The cancel and the deduction are racing each other, and you can't control the order.

Option D: Async Cancel with Retry

OK, so you send the cancel asynchronously and retry it a few times with delays. That should handle the race condition, right?

But now consider: what if the user, not seeing a response, hits the "Pay" button again? Now you have two deduction attempts in flight, and your cancel logic is trying to cancel both. The state space is exploding.

The Real Problem

The fundamental issue is that your cancel operation operates on the order, not on the transaction. You're saying "cancel the order" when you should be saying "cancel this specific deduction attempt."

The fix: introduce a transaction ID (trans_id) that binds the deduction and its corresponding cancellation together.

The Solution: Transaction ID

Generate a unique trans_id for each deduction attempt. Pass it to the card system. When you cancel, cancel by trans_id, not by order ID.

Now the card system can match deductions and cancellations precisely. A cancel with trans_id = T1 will only affect the deduction with trans_id = T1, even if there are other deductions for the same order in flight.

What Should trans_id Be?

The trans_id needs to be unique, but it also needs to carry ordering information. Why? Because the card system needs to know which operation came first — a deduction or a cancellation with the same trans_id.

Use a millisecond timestamp as the trans_id. This gives you:

  • Uniqueness: millisecond timestamps are unique enough for transaction IDs.
  • Ordering: you can tell which operation happened first by comparing timestamps.

The Complete Flow

Let's walk through the revised flow with trans_id:

Deduction Flow

  1. Generate trans_id = current millisecond timestamp.
  2. Send deduction request to card system with trans_id.
  3. If success response: mark order as paid, done.
  4. If failure response: mark order as unpaid, done.
  5. If timeout: enter the recovery flow.

Recovery Flow (After Timeout)

  1. Send a cancel request with the same trans_id.
  2. The card system matches the cancel against the deduction by trans_id:
    • If the deduction hasn't happened yet: the cancel "wins." Any subsequent deduction with this trans_id will be rejected.
    • If the deduction already happened: the deduction "wins." The cancel triggers a refund.
    • If both arrive simultaneously: the card system uses the timestamp ordering to decide.
  3. Query the result of the cancel/deduction to determine the final state.
  4. If the query times out, retry with exponential backoff.

What About User Retries?

If the user hits "Pay" again, you generate a new trans_id (because the millisecond timestamp has changed). The new deduction attempt is completely independent of the previous one. The card system treats them as separate transactions.

The old trans_id's cancel/deduction resolution continues in the background, unaffected by the new attempt.

So What?

This example is deceptively simple. A prepaid card deduction — how hard could it be? Yet we've had to deal with:

  • Timeouts (the root of most distributed systems problems)
  • Race conditions between concurrent operations
  • The distinction between orders and transactions
  • Idempotency and unique transaction identification
  • Ordering guarantees in asynchronous systems

And this is just one step in the flow. Real systems have dozens of such steps, each with its own failure modes, each interacting with the others.

Over 90% of bugs in distributed systems come from inadequate handling of failure scenarios.

The happy path is usually straightforward. It's the timeouts, the retries, the partial failures, the race conditions, and the recovery flows that make programming hard. And these failure scenarios are combinatorially explosive — each additional step multiplies the possible failure states.

Is There Hope?

Yes, but with a caveat: not all systems need the same level of reliability.

The gas station payment system needs to handle failures meticulously because money is involved. But what about a blog's view counter? If a view gets lost or double-counted, nobody cares. You can use a simple fire-and-forget increment with no error handling at all.

The key is to evaluate the cost of failure against the cost of robustness:

  • High cost of failure (payments, inventory, medical systems): invest heavily in failure handling. Use transactions, idempotency keys, distributed locks, sagas, and whatever else it takes.
  • Low cost of failure (analytics, notifications, view counters): keep it simple. Accept occasional losses or duplicates. The cost of over-engineering exceeds the cost of the occasional failure.
  • Medium cost of failure: find a pragmatic middle ground. Maybe use eventual consistency with periodic reconciliation instead of real-time guarantees.

The Programmer's Responsibility

Good programmers don't just code the happy path. They think about failure modes before they write code. They ask:

  • What happens if this call times out?
  • What happens if this process crashes right here?
  • What happens if this message is delivered twice?
  • What happens if this response is lost?
  • What happens if two users trigger this at the same time?

This is what "failure-oriented programming" means. It's not pessimism — it's realism. Distributed systems are unreliable by nature. Networks partition. Processes crash. Clocks drift. Messages get delayed, duplicated, or lost.

The code that handles these failures is often 80% of the total code. And it's the hardest 80% to write, test, and debug.

Key Takeaways

  • Timeouts are the root of evil. A timeout doesn't mean failure. It means "I don't know." Treat it accordingly.
  • Identify transactions, not just operations. Use unique IDs (like trans_id) to bind related operations together and resolve races.
  • Ordering matters. In asynchronous systems, operations can arrive in unexpected orders. Design your protocols to handle this.
  • Idempotency is your friend. If an operation can be retried, make it safe to retry. Idempotent operations are the foundation of reliable distributed systems.
  • Match reliability to cost. Not everything needs five-nines availability. Evaluate the cost of failure and invest accordingly.
  • Failure handling is the hard part. The happy path is easy. The value of a programmer lies in their ability to handle the unhappy paths correctly and elegantly.

Programming is hard because failure is complex. Embrace that complexity, design for it explicitly, and you'll write systems that actually work in production — not just in demos.
