Distributed Transaction Design: Lessons from a Prepaid Card Recharge System

2020-04-20 | Distributed Systems

The Original Implementation

The prepaid card recharge system started with a deceptively simple implementation. A user would select a card, choose a recharge amount, and the system would:

  1. Deduct the amount from the user's payment account.
  2. Credit the amount to the prepaid card balance.
  3. Record the transaction.

All of this logic lived in a single service, with the payment deduction and card recharge executed sequentially in the same transaction. There was no distributed transaction handling to speak of. It worked fine most of the time — until it didn't.

The Problems

No Failure Handling

The original implementation assumed a happy path where every step succeeds. If the card recharge failed after the payment was deducted, the user's money was simply lost. There was no rollback, no compensation, and no reconciliation. This is unacceptable for a financial system.

Business Logic in the Wrong Place

Most of the business logic resided in the frontend controller or the orchestration layer, rather than in a dedicated domain service. The controller was making decisions about payment validation, balance calculation, and error handling. This violated the separation of concerns and made the code difficult to test and maintain.

No Pre-check

The system did not validate whether the recharge was legal before executing it. For example, it did not check whether the card was active, whether the amount exceeded the card's maximum balance, or whether the user's account had sufficient funds. These checks happened implicitly during the transaction, leading to confusing error messages and partial failures.

Assumption That Card Recharge Always Succeeds

The original code treated the card recharge as an infallible operation. In reality, the card system is a separate service with its own failure modes: network timeouts, database deadlocks, service restarts, and so on. Assuming it always succeeds is a recipe for data inconsistency.

The Refactoring

Separate Recharge Service

The first step was to extract the recharge logic into a dedicated RechargeService. This service became the single owner of the recharge business rules: validating the card, checking limits, calculating the new balance, and recording the transaction. The controller was reduced to a thin adapter that delegated to the service.

Pre-check Legality

Before any money moves, the RechargeService performs a comprehensive pre-check:

  • Is the card active and not frozen?
  • Will the new balance exceed the card's maximum allowed balance?
  • Does the user have sufficient funds in their payment account?
  • Are there any pending transactions on this card?

If any check fails, the recharge is rejected immediately, before any state changes occur. This prevents partial failures and makes error handling much cleaner.

Handle Recharge Failure

If the pre-check passes but the actual card recharge fails (e.g., the card service returns an error), the system must refund the payment. This introduces the classic distributed transaction problem: how do you ensure that the payment deduction and the card recharge are either both committed or both rolled back, when they involve two separate services?

The Timeout Problem

The naive approach to handling recharge failure is: if the recharge fails, refund the payment immediately. But this breaks down when the failure is a timeout.

Consider this scenario:

  1. The system deducts the payment successfully.
  2. The system calls the card recharge service.
  3. The card recharge service processes the request successfully and credits the card.
  4. But the response is lost due to a network issue, and the calling system receives a timeout.

From the calling system's perspective, the recharge failed (timeout). If it immediately refunds the payment, the user has been refunded and the card has been credited. The user now has more money than they started with, and the system has lost money.

You cannot assume that a timeout means failure. The remote operation may have succeeded; you just don't know.

Query Before Refund Does Not Work Either

A common workaround is: before refunding, query the card service to check whether the recharge actually went through. If the card balance was updated, do not refund. If it was not, proceed with the refund.

This approach has its own problems:

  • The query itself might timeout. If the network is unreliable, the query is just as likely to fail as the original request, leaving you in the same uncertain state.
  • The recharge might still be in progress. The card service may have received the request and is still processing it. A query at this moment would return "not yet credited," prompting a refund, but then the recharge completes, and you have the same double-credit problem.
  • There is a race condition between the query and the recharge completion. No matter how you slice it, you cannot atomically determine the state of the remote system.

The Solution: Scheduled Reconciliation

The robust solution is to accept uncertainty and defer the resolution. Instead of trying to determine the outcome immediately, the system:

  1. Records the recharge attempt as "pending" in a local transaction log.
  2. If the recharge response is a clear success, marks the transaction as "completed."
  3. If the recharge response is a clear failure (not a timeout), marks the transaction as "failed" and initiates a refund.
  4. If the recharge response is a timeout, leaves the transaction as "pending" and does nothing immediately.
  5. A scheduled reconciliation task runs periodically (e.g., every hour) and scans all "pending" transactions that are older than a threshold (e.g., 1 hour). For each pending transaction, it queries the card service to determine the actual outcome and takes the appropriate action (complete or refund).

The one-hour delay is critical. It provides a generous window for any in-flight operations to complete and for transient network issues to resolve. By the time the reconciliation task runs, the state of the recharge is almost certainly determinable.

Pre-charging: The "Recharging" Record

To further strengthen the system, we introduced the concept of pre-charging. The flow becomes:

  1. Before deducting the payment, create a transaction record with status "recharging" in the local database.
  2. Deduct the payment.
  3. Call the card recharge service.
  4. If the recharge succeeds, update the transaction record to status "success."
  5. If the recharge clearly fails, update the transaction record to status "refunded" and initiate the refund.
  6. If timeout, leave the record as "recharging" for the reconciliation task to handle.

The "recharging" record acts as a sentinel. It ensures that even if the system crashes between the payment deduction and the card recharge, the transaction is not lost. The reconciliation task will pick it up and resolve it.

Key Lessons

Remote Calls Lack Ordering Guarantees

In a distributed system, you cannot assume that operations happen in a specific order. A call that you made first may complete after a call you made second. A response that you expected to receive may be delayed, duplicated, or lost entirely. Design your system to handle all of these possibilities.

Minimize the Probability of Exceptions

While you cannot eliminate failures, you can minimize their probability. Pre-checks, idempotency keys, and circuit breakers all help reduce the chance of entering an inconsistent state. The less likely a failure is, the less often the reconciliation task has to clean up.

Add Reconciliation Sentinels

Every distributed transaction should have a reconciliation mechanism. This is typically a scheduled task that scans for unresolved transactions and brings them to a consistent state. The sentinel is the safety net that catches all the edge cases you could not handle in real time.

In distributed systems, consistency is not achieved by preventing failures; it is achieved by detecting and repairing inconsistencies after they occur.

Summary

The prepaid card recharge system taught us that distributed transactions cannot be handled with simple request-response patterns. Timeouts are not failures; they are uncertainties. Querying for the outcome is not a silver bullet; it introduces its own race conditions. The only reliable approach is to embrace eventual consistency: record the intent, attempt the operation, and reconcile the outcomes asynchronously.

The three pillars of a robust distributed transaction design are:

  1. Pre-check — validate everything before changing any state.
  2. Minimize exceptions — use idempotency, timeouts, and circuit breakers to reduce failure probability.
  3. Reconcile — always have a sentinel that detects and repairs inconsistencies.
