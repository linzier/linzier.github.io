Character Encoding (Part 3): Unicode

2022-02-28 | Encoding

In the first two articles of this series, we explored the pre-Unicode world of incompatible encodings and the four-layer character encoding model. Now we arrive at the hero of our story: Unicode, the universal character encoding that finally brought order to the chaos.

The Origins of Unicode

The story begins in 1987, when two engineers — Joe Becker from Apple and Lee Collins from Xerox — began investigating the feasibility of a universal character set. Their goal was ambitious: create a single encoding that could represent every character in every writing system on Earth.

At the time, many people thought this was impossible. How could you fit tens of thousands of Chinese characters, thousands of Korean Hangul syllables, and hundreds of other scripts into a single encoding? The existing approach — separate encodings for each language group — seemed like the only practical option.

Becker and Collins made several key findings that changed the conversation:

  1. Two bytes are sufficient. Careful analysis showed that 16 bits (65,536 possible values) could accommodate all characters in current use across all modern writing systems, with room to spare. This was a revelation: a universal encoding did not require 32-bit code points.
  2. Fixed-width encoding is preferred. Variable-width encodings (like the pre-Unicode CJK encodings) are harder to process. Searching, sorting, and indexing are all simpler when every character has the same width. With 16 bits, a fixed-width encoding was feasible.
  3. CJK characters can be unified. Chinese, Japanese, and Korean all use Chinese characters (hanzi/kanji/hanja). Many of these characters are identical or nearly identical across the three languages. By unifying them — assigning the same code point to the same character regardless of which language uses it — the total number of required code points was dramatically reduced.

Armed with these findings, Becker drafted the Unicode 88 proposal in 1988. The proposal outlined a 16-bit fixed-width encoding that could represent all modern characters.

In 1991, the Unicode Consortium was founded, and Unicode 1.0 was published. This first release contained 7,161 characters covering 24 scripts. It was a start, but it was far from complete — CJK characters were not yet included.

The big expansion came in 1992 with Unicode 1.0.1, which added CJK unified ideographs (over 20,000 characters). Suddenly, Unicode could handle Chinese, Japanese, and Korean text. The dream of a universal encoding was becoming reality.

UCS: The Parallel Effort at ISO

While the Unicode Consortium was working on Unicode, the International Organization for Standardization (ISO) was developing its own universal encoding: the Universal Coded Character Set (UCS), defined in the ISO/IEC 10646 standard.

UCS and Unicode were remarkably similar. Both aimed to encode all the world's characters. Both used similar code point assignments. But they were developed independently, and there were subtle differences in scope and structure.

Recognizing the absurdity of maintaining two nearly identical standards, the Unicode Consortium and ISO reached an agreement in 1991–1993 to merge the two efforts. From that point on, Unicode and UCS have been kept in sync. The Unicode standard references ISO/IEC 10646, and the two standards share the same code points. Today, "Unicode" and "UCS" are effectively interchangeable, though "Unicode" is the more commonly used name.

Unicode Overview

It is critical to understand that Unicode encodes abstract characters, not glyphs. A glyph is a specific visual representation of a character — the way it looks on a screen or page. A character is the abstract concept itself.

For example, the Latin letter "A" has many glyphs: A, A, A, A, A. These are all different glyphs, but they all represent the same abstract character: "Latin Capital Letter A." Unicode assigns this character the code point U+0041, regardless of how it is rendered.

Code Points

A code point is the numerical value assigned to an abstract character. Code points are written in hexadecimal with the prefix "U+", like U+0041 or U+4E2D.

The Unicode codespace ranges from U+0000 to U+10FFFF, giving a total of 1,114,112 possible code points. As of Unicode 15.0 (2022), about 149,000 code points are assigned. The rest are reserved for future use or intentionally left unassigned.

Planes

The 1,114,112 code points are divided into 17 planes, each containing 65,536 (0x10000) code points:

  • Plane 0: The Basic Multilingual Plane (BMP). U+0000 to U+FFFF. This plane contains almost all modern scripts, common symbols, and CJK characters. The vast majority of text you encounter is in the BMP.
  • Planes 1–16: Supplementary Planes. U+10000 to U+10FFFF. These planes contain less common characters: historical scripts (Egyptian hieroglyphs, cuneiform), rare CJK characters, emoji, musical symbols, and more.

Plane 1 (U+10000 to U+1FFFF) is called the Supplementary Multilingual Plane (SMP). Plane 2 (U+20000 to U+2FFFF) is the Supplementary Ideographic Plane (SIP), which contains rare CJK characters. Planes 3–13 are mostly unreserved. Plane 14 (U+E0000 to U+EFFFF) is the Supplementary Special-purpose Plane (SSP), used for special tags. Planes 15 and 16 are the Supplementary Private Use Area Planes (SPUA), available for private use.

The Three Encoding Forms

Unicode defines the code points, but how do we turn those code points into bytes? That is the job of the three Unicode encoding forms: UTF-8, UTF-16, and UTF-32.

UTF-16: The Original Fixed-Width Encoding

When Unicode 1.0 was designed, the plan was simple: use 16 bits (2 bytes) for every character. With 65,536 possible values, there was plenty of room for all modern characters. UTF-16 was born as a fixed-width, 16-bit encoding.

But then reality intruded. The CJK unification project revealed that there were more than 65,536 characters that needed to be encoded. The 16-bit codespace was not big enough.

The solution was surrogate pairs. Code points in the BMP (U+0000 to U+FFFF) are encoded as a single 16-bit code unit. Code points above U+FFFF (in the supplementary planes) are encoded as a pair of 16-bit code units, drawn from reserved ranges in the BMP called the surrogate ranges:

  • High surrogates: U+D800 to U+DBFF
  • Low surrogates: U+DC00 to U+DFFF

A high surrogate followed by a low surrogate represents a single supplementary character. The two code units together encode a 20-bit offset, which is added to U+10000 to get the actual code point.

For example, the emoji U+1F600 (grinning face) is encoded in UTF-16 as:

Code point: U+1F600
Subtract 0x10000: 0xF600
High 10 bits: 0x3D8 → high surrogate: U+D800 + 0x3D8 = U+D83D
Low 10 bits: 0x200 → low surrogate:  U+DC00 + 0x200 = U+DE00
UTF-16: 0xD83D 0xDE00

UTF-16 is now a variable-width encoding: characters are either 2 or 4 bytes. This was a significant compromise from the original fixed-width design, but it was necessary to accommodate the full Unicode codespace.

UTF-16 is the encoding used internally by Java, C#, JavaScript, and Windows. These systems represent strings as sequences of 16-bit code units, and supplementary characters are handled via surrogate pairs.

UTF-8: The Encoding That Won

UTF-8 was designed by Ken Thompson (of Unix fame) and Rob Pike in 1992–1993. It uses 8-bit code units (bytes) and encodes each code point using one to four bytes:

  • U+0000 to U+007F: 1 byte (0xxxxxxx)
  • U+0080 to U+07FF: 2 bytes (110xxxxx 10xxxxxx)
  • U+0800 to U+FFFF: 3 bytes (1110xxxx 10xxxxxx 10xxxxxx)
  • U+10000 to U+10FFFF: 4 bytes (11110xxx 10xxxxxx 10xxxxxx 10xxxxxx)

The brilliance of UTF-8 lies in its ASCII compatibility. The first 128 code points (U+0000 to U+007F) are encoded as single bytes that are identical to ASCII. This means:

  • Any ASCII text is automatically valid UTF-8.
  • UTF-8 can be safely processed by software that only understands ASCII (as long as it does not try to interpret non-ASCII bytes).
  • Legacy ASCII files do not need to be converted; they are already UTF-8.

This backward compatibility was the key reason UTF-8 won the encoding wars. The world had billions of lines of ASCII text and decades of software that assumed ASCII. UTF-8 could coexist with this legacy; UTF-16 and UTF-32 could not.

UTF-8 also has other desirable properties:

  • Self-synchronizing. You can find character boundaries in a byte stream without reading from the beginning. The leading byte of each character has a distinctive pattern (11...0), and continuation bytes have the pattern 10xxxxxx.
  • Byte-order independent. Unlike UTF-16 and UTF-32, UTF-8 has no byte order issues. A byte is a byte, regardless of the CPU's endianness.
  • Compact for ASCII-heavy text. English text encoded in UTF-8 is the same size as ASCII. For text that is mostly ASCII with occasional non-ASCII characters (like HTML with English tags and occasional accented words), UTF-8 is very space-efficient.

Today, UTF-8 is the dominant encoding on the web. Over 98% of web pages use UTF-8. It is the default encoding for HTML5, XML, JSON, and most modern protocols.

UTF-32: The Simple but Wasteful Encoding

UTF-32 is the simplest encoding: every code point is represented by exactly one 32-bit code unit. It is a fixed-width encoding where character n is always at byte offset n×4.

UTF-32 is rarely used for text storage or transmission because it wastes a lot of space. Most text has code points well below U+10000, so the upper two bytes of each 4-byte code unit are usually zero. UTF-32 text is roughly twice the size of UTF-16 text and three to four times the size of UTF-8 text for ASCII-heavy content.

However, UTF-32 is useful internally in some text processing systems. When you need to index into a string by character position, UTF-32 makes it trivial: the nth character is at offset n×4. With UTF-8 or UTF-16, you have to scan from the beginning to find the nth character because characters have variable widths.

The Compromises: Compatibility vs. Purity

Unicode's design philosophy prioritizes round-trip compatibility with existing encodings. This means that if a character existed in a pre-Unicode encoding, Unicode should be able to represent it, and converting from the old encoding to Unicode and back should produce the original bytes.

This principle led to some unfortunate compromises. The most notable is the existence of duplicate code points: different code points that represent the same abstract character.

The classic example is the Kelvin sign (U+212A, "K") and the Latin capital letter K (U+004B, "K"). Visually, they are identical. Semantically, they represent the same letter. But Unicode assigns them different code points because the Kelvin sign existed as a distinct character in some pre-Unicode encodings, and round-trip compatibility required preserving that distinction.

Similarly, the Angstrom sign (U+212B, "Å") is a duplicate of Latin capital letter A with ring above (U+00C5, "Å"). The Ohm sign (U+2126) is a duplicate of Latin capital letter Omega (U+03A9, "Ω").

The Unicode standard recommends treating these duplicates as equivalent (using a process called normalization), but they exist in the codespace for historical reasons. This is a pragmatic compromise: purity was sacrificed for compatibility, and the result is an encoding that could actually be adopted in the real world.

Summary

  1. Unicode was born from the vision of a universal character set, made possible by the insight that 16 bits were enough for all modern characters and that CJK characters could be unified.
  2. Unicode and UCS (ISO/IEC 10646) were developed in parallel and merged in 1991–1993. They are now effectively the same standard.
  3. Unicode encodes abstract characters, not glyphs. Code points are written as U+XXXX.
  4. The Unicode codespace has 17 planes. Plane 0 (the BMP) contains almost all modern text. Planes 1–16 contain supplementary characters.
  5. Three encoding forms: UTF-16 (variable-width, 2 or 4 bytes, used by Java/C#/JS/Windows), UTF-8 (variable-width, 1–4 bytes, ASCII-compatible, dominant on the web), and UTF-32 (fixed-width, 4 bytes, used internally for indexing).
  6. Round-trip compatibility with legacy encodings led to duplicate code points (e.g., Kelvin sign vs. Latin K). This is a pragmatic compromise that enabled widespread adoption.

Unicode is not perfect, but it is the best we have. It is a testament to the power of standards and the importance of pragmatism in engineering design. And it is the foundation of all modern text processing.
