DNS Explained: The Complete Story

2022-01-10 | Networking

Every time you visit a website, send an email, or use a mobile app, a silent hero works behind the scenes to make it happen. It translates the human-friendly name you typed (www.google.com) into the machine-friendly IP address (142.250.80.46) that computers use to find each other. This is DNS, the Domain Name System — the internet's phone book.

What DNS Does

Computers communicate using IP addresses: numbers like 142.250.80.46 (IPv4) or 2607:f8b0:4004:800::200e (IPv6). But humans are terrible at remembering long strings of numbers. We prefer names: www.google.com, mail.google.com, api.github.com.

DNS is the system that bridges this gap. It translates domain names into IP addresses (and vice versa), along with a variety of other useful information about domain names.

When you type www.google.com into your browser, here is what happens:

  1. Your browser asks the DNS system: "What is the IP address of www.google.com?"
  2. The DNS system responds: "142.250.80.46."
  3. Your browser connects to 142.250.80.46 and loads the page.

This translation happens in milliseconds, and you never see it. But without DNS, you would have to memorize the IP address of every website you want to visit. The internet would be unusable.

The DNS Hierarchy

DNS is not a single database. If it were, it would be a single point of failure and a performance bottleneck. Instead, DNS is a distributed, hierarchical database.

The hierarchy has three main levels:

Root Servers

At the top of the hierarchy are the root servers. There are 13 sets of root servers (labeled A through M), operated by various organizations around the world. (Each "set" is actually a cluster of hundreds of servers using anycast, so there are over 1,300 physical servers worldwide.)

The root servers do not know the IP address of www.google.com. But they know who is responsible for each top-level domain (TLD). When you ask a root server about www.google.com, it responds: "I do not know, but ask the .com servers. Here are their addresses."

TLD Servers

The next level is the TLD servers. There are TLD servers for each top-level domain: .com, .org, .net, .cn, .uk, and so on. There are also TLD servers for country-code TLDs (ccTLDs) like .cn (China), .uk (United Kingdom), and .jp (Japan).

The .com TLD servers know who is responsible for each domain under .com. When you ask them about www.google.com, they respond: "I do not know, but Google's domain is managed by these name servers. Here are their addresses."

Authoritative Servers

At the bottom of the hierarchy are the authoritative name servers. These are the servers that actually know the IP addresses for specific domains. Google operates its own authoritative servers for google.com. When you ask them about www.google.com, they respond: "The IP address of www.google.com is 142.250.80.46."

This hierarchical design has several advantages:

  • Distributed: No single point of failure. If one root server goes down, the other 12 sets continue to operate.
  • Scalable: Each level only needs to know about the level below it. The root servers do not need to know about every domain on the internet.
  • Delegated: Domain owners can manage their own DNS records without involving a central authority.

Recursive vs. Iterative Queries

When your computer needs to resolve a domain name, it could theoretically follow the hierarchy itself: ask a root server, then a TLD server, then an authoritative server. But this would be slow and inefficient. Instead, DNS uses two types of queries:

Recursive Queries

In a recursive query, you ask a DNS server to find the answer for you, and it does all the work. You say: "What is the IP address of www.google.com?" and the server responds with the final answer (or an error).

Your computer sends recursive queries to a recursive resolver (also called a recursive name server). This is usually operated by your ISP, or you can use a public resolver like Google Public DNS (8.8.8.8) or Cloudflare (1.1.1.1).

Iterative Queries

In an iterative query, the DNS server does not do all the work for you. Instead, it gives you the best answer it can based on its knowledge. If it does not know the answer, it says: "I do not know, but here is a server that might know."

The recursive resolver uses iterative queries to work its way down the hierarchy:

  1. It asks a root server: "What is the IP address of www.google.com?" The root server responds: "I do not know, but ask the .com TLD servers. Here are their addresses."
  2. It asks a .com TLD server: "What is the IP address of www.google.com?" The TLD server responds: "I do not know, but ask Google's authoritative servers. Here are their addresses."
  3. It asks Google's authoritative server: "What is the IP address of www.google.com?" The authoritative server responds: "142.250.80.46."
  4. The recursive resolver returns the answer to your computer.

From your computer's perspective, it was a single recursive query. Behind the scenes, the resolver performed three iterative queries to find the answer.

DNS Records

DNS does not just map domain names to IP addresses. It supports a variety of record types, each serving a different purpose.

A Record (Address Record)

The most basic record type. An A record maps a domain name to an IPv4 address.

www.example.com.  IN  A  93.184.216.34

This says: "The IPv4 address of www.example.com is 93.184.216.34."

AAAA Record (Quad-A Record)

Like an A record, but for IPv6 addresses.

www.example.com.  IN  AAAA  2606:2800:220:1:248:1893:25c8:1946

CNAME Record (Canonical Name Record)

A CNAME record maps one domain name to another (an alias). This is useful when you want multiple domain names to point to the same server.

blog.example.com.  IN  CNAME  www.example.com.

This says: "blog.example.com is an alias for www.example.com. To find blog.example.com, look up www.example.com."

CNAME records are commonly used with CDNs and cloud services. For example, if you host your site on a platform like Vercel or Netlify, you might have:

www.mysite.com.  IN  CNAME  cname.vercel-dns.com.

MX Record (Mail Exchange Record)

An MX record specifies the mail server responsible for receiving email on behalf of a domain. It includes a priority value: lower numbers indicate higher priority.

example.com.  IN  MX  10  mail.example.com.
example.com.  IN  MX  20  mail2.example.com.

This says: "Email for example.com should be delivered to mail.example.com (priority 10). If that server is unavailable, try mail2.example.com (priority 20)."

NS Record (Name Server Record)

An NS record specifies the authoritative name servers for a domain. It delegates a DNS zone to a set of name servers.

example.com.  IN  NS  ns1.example.com.
example.com.  IN  NS  ns2.example.com.

This says: "The authoritative name servers for example.com are ns1.example.com and ns2.example.com."

TXT Record (Text Record)

A TXT record holds arbitrary text. It is commonly used for domain verification and email security.

example.com.  IN  TXT  "v=spf1 include:_spf.google.com ~all"

This is an SPF (Sender Policy Framework) record that specifies which mail servers are authorized to send email on behalf of example.com. TXT records are also used for DKIM (DomainKeys Identified Mail) and DMARC (Domain-based Message Authentication, Reporting, and Conformance).

Other Record Types

There are many other DNS record types:

  • SOA (Start of Authority): Contains administrative information about a DNS zone (primary name server, admin email, serial number, refresh intervals).
  • PTR (Pointer): Used for reverse DNS lookups (mapping an IP address back to a domain name).
  • SRV (Service): Specifies the location of servers for specific services (e.g., SIP, XMPP).
  • CAA (Certificate Authority Authorization): Specifies which certificate authorities are allowed to issue certificates for a domain.

DNS Caching

If every DNS query required a full recursive lookup (root → TLD → authoritative), the internet would be painfully slow. Fortunately, DNS makes extensive use of caching.

TTL (Time to Live)

Every DNS record has a TTL (Time to Live) value, specified in seconds. The TTL tells caches how long they can keep the record before they need to ask again.

www.example.com.  3600  IN  A  93.184.216.34

This says: "The IP address of www.example.com is 93.184.216.34, and you can cache this answer for 3600 seconds (1 hour)."

A short TTL (e.g., 60 seconds) means the record changes frequently and caches should not hold it for long. A long TTL (e.g., 86400 seconds = 1 day) means the record is stable and can be cached aggressively.

Levels of Caching

DNS caching happens at multiple levels:

  1. Browser cache: Your browser caches DNS responses. The next time you visit the same website, the browser uses the cached IP address without querying DNS.
  2. OS cache: Your operating system also caches DNS responses. On Linux, you can flush the cache with systemd-resolve --flush-caches. On macOS, sudo dscacheutil -flushcache. On Windows, ipconfig /flushdns.
  3. ISP resolver cache: Your ISP's recursive resolver caches responses. When you query the resolver, it checks its cache first. If the answer is cached and not expired, it returns the cached answer without performing a new lookup.
  4. Public resolver cache: Public resolvers like Google DNS (8.8.8.8) and Cloudflare (1.1.1.1) also cache responses. Because they serve millions of users, their caches are very effective.

Caching is why DNS queries are usually so fast. Most of the time, the answer is already in a cache somewhere, and no recursive lookup is needed.

Smart DNS and CDN

DNS is not just about translating names to IP addresses. It is also a powerful tool for traffic management and content delivery.

Smart DNS (GeoDNS)

Smart DNS (also called GeoDNS) returns different IP addresses based on the geographic location of the requester. This is useful for serving users from the nearest data center.

For example, a user in Beijing who queries www.example.com might get the IP address of a server in Beijing, while a user in New York gets the IP address of a server in Virginia.

Smart DNS works by examining the IP address of the recursive resolver (or the end user, if using EDNS Client Subnet) and returning the appropriate IP address based on geographic rules.

DNS and CDN

CDNs (Content Delivery Networks) rely heavily on DNS to route users to the nearest edge server. When you access a CDN-hosted website, the DNS resolution process looks something like this:

  1. You query www.example.com.
  2. The authoritative server for example.com returns a CNAME pointing to the CDN: www.example.com.cdn.cloudflare.net.
  3. Your resolver follows the CNAME and queries www.example.com.cdn.cloudflare.net.
  4. Cloudflare's authoritative server examines your location (based on your resolver's IP) and returns the IP address of the nearest Cloudflare edge server.

This is why CDNs use CNAME records: they need to intercept the DNS resolution process and return a location-specific IP address. The CNAME allows the CDN to control the DNS response for a customer's domain.

Setting Up Your Own Authoritative DNS

If you own a domain, you need to configure authoritative DNS so that the world can find your website, receive your email, and use your services.

Choosing a DNS Provider

You have several options:

  • Your registrar's DNS: Most domain registrars (GoDaddy, Namecheap, etc.) offer free DNS hosting. This is the simplest option but may lack advanced features.
  • Cloud DNS providers: Services like Cloudflare DNS, AWS Route 53, Google Cloud DNS, and Azure DNS offer robust, globally distributed DNS hosting with advanced features like GeoDNS, DNSSEC, and DDoS protection.
  • Self-hosted: You can run your own authoritative DNS servers using software like BIND, PowerDNS, or NSD. This gives you full control but requires expertise and infrastructure.

Configuring DNS Records

Once you have chosen a provider, you need to configure your DNS records. A typical setup for a domain might look like this:

; Name servers
example.com.  IN  NS  ns1.example.com.
example.com.  IN  NS  ns2.example.com.

; A records
example.com.       IN  A      93.184.216.34
www.example.com.   IN  A      93.184.216.34
mail.example.com.  IN  A      93.184.216.35

; AAAA records (IPv6)
example.com.       IN  AAAA  2606:2800:220:1:248:1893:25c8:1946

; MX records
example.com.  IN  MX  10  mail.example.com.

; TXT records (SPF)
example.com.  IN  TXT  "v=spf1 mx -all"

; CAA record
example.com.  IN  CAA  0 issue "letsencrypt.org"

Delegating Your Domain

After configuring your DNS records, you need to tell the world where to find your authoritative servers. This is done by setting the name server (NS) records at your domain registrar.

For example, if you are using Cloudflare DNS, you would set your domain's name servers to something like:

ns1.cloudflare.com
ns2.cloudflare.com

The registrar then updates the TLD servers (e.g., the .com servers) to point to your authoritative servers. This process is called delegation.

Delegation can take up to 48 hours to propagate across the internet, though it usually happens much faster.

Testing Your DNS

You can test your DNS configuration using various tools:

  • dig: A command-line tool for querying DNS. dig www.example.com shows the full DNS response, including all records and the resolution path.
  • nslookup: A simpler command-line tool. nslookup www.example.com returns the IP address.
  • Online tools: Websites like DNSViz, IntoDNS, and MXToolbox can check your DNS configuration for errors and provide recommendations.

Summary

  1. DNS translates domain names into IP addresses, making the internet usable for humans.
  2. DNS is a distributed, hierarchical database with three levels: root servers, TLD servers, and authoritative servers.
  3. Recursive queries ask a resolver to find the answer; iterative queries return the best partial answer. Resolvers use iterative queries to work their way down the hierarchy.
  4. DNS supports many record types: A (IPv4), AAAA (IPv6), CNAME (alias), MX (mail), NS (name server), TXT (text), and more.
  5. DNS caching at multiple levels (browser, OS, ISP resolver, public resolver) makes DNS fast. TTL controls how long records are cached.
  6. Smart DNS and CDN use DNS to route users to the nearest server based on geographic location.
  7. Setting up authoritative DNS involves choosing a provider, configuring records, and delegating your domain at the registrar.

DNS is one of the most important and most taken-for-granted protocols on the internet. It is the silent hero that makes every web visit, every email, and every app connection possible. The next time you type a URL and a page loads instantly, take a moment to appreciate the incredible machinery of DNS working behind the scenes.
