Character Encoding (Part 4): UTF

2022-03-12 | Encoding

The previous article, Character Encoding (Part 3): Unicode, introduced the Unicode standard and its three primary implementation forms: UTF-16, UTF-8, and UTF-32. This entry explores the technical details of each format.

UTF stands for Unicode Transformation Format. It operates at the third and fourth layers of the character encoding model (the Character Encoding Form and Character Encoding Scheme). The responsibility of any UTF variant is to serialize abstract Unicode code points into physical code units for memory and storage.

The numerical suffix *X* in UTF-X indicates the bit-width of its fundamental code unit. For instance, UTF-16 relies on 16-bit code units, whereas UTF-8 operates on 8-bit bytes.

UTF-16

When Unicode was initially conceived, it was designed as a fixed-width 16-bit encoding. Under this original blueprint, a character's code point was identical to its in-memory representation.

For example, the Chinese character "啊" (ah) maps to the Unicode code point U+554A. In-memory, it was represented directly by the 16-bit sequence 55 4A (binary: 01010101 01001010).

This implementation was simple and fast, requiring no bitwise transformations, offset adjustments, or flag bits. This simplicity is why early operating systems and runtimes adopted 16-bit fixed-width strings.

However, a 16-bit codespace is capped at $2^{16} = 65,536$ unique entries. The Unicode Consortium soon realized this was inadequate to catalog all global scripts and historical ideographs, so they expanded the codespace to 10FFFF. The original fixed-width design had to be revised.

To overcome this limitation, they redesigned UTF-16.

The revised UTF-16 specification uses a variable-width encoding, mapping characters to one or two 16-bit code units. Code points in the Basic Multilingual Plane (BMP, U+0000 to U+FFFF) occupy a single 16-bit code unit, while characters in the supplementary planes are encoded as a pair of 16-bit code units.

For example, given the byte sequence 01001110 00101101 01010110 11111101, should a parser interpret this as two independent BMP characters (each occupying one 16-bit code unit) or as some other structure?

An identical design problem appeared in GB 2312. To remain backward-compatible with single-byte ASCII, GB 2312 uses one byte for English characters and two bytes for Chinese characters. To distinguish whether a byte is a standalone ASCII character or the lead byte of a Chinese character, GB 2312 reserves the highest bit as a flag: if the highest bit is 0, it is standalone ASCII; if 1, it pairs with the following byte.

UTF-16 (and UTF-8, as we will discuss later) adopts a similar flag-based approach. The leading *n* bits of each code unit serve as metadata flags indicating whether the unit is standalone or part of a pair. Under this scheme, a UTF-16 code unit can be visualized as xxxxyyyyyyyyyyyy, where the prefix x represents the control flags and y represents the actual payload bits. The parser inspects the value of x to determine how to proceed.

Unicode's absolute codespace ceiling is 10FFFF, which translates to the 21-bit binary value 1 0000 1111 1111 1111 1111. Values up to FFFF (binary: 0000 1111 1111 1111 1111, where the upper 5 bits are 0 and only the lower 16 bits vary) can be represented by a single code unit. Code points exceeding FFFF require a surrogate pair of two code units, structured conceptually as: xxxxyyyyyyyyyyyy xxxxyyyyyyyyyyyy.

For this two-unit pairing to work reliably, several conditions must be satisfied:

  1. The control flags (x) must follow a unique, recognizable bit pattern so the parser can identify them instantly;
  2. The payload bits (y) must have enough capacity to hold the entire range of supplementary plane values: $10FFFF - FFFF = 100000$ (or decimal: $1,114,111 - 65,535 = 1,048,576$ possible values);
  3. The flag patterns of the two code units must differ so the parser can determine which unit is the "lead" and which is the "trail."

To represent exactly $1,048,576$ values ($1024 \times 1024$), we need exactly 10 payload bits (y) in each of the two code units ($2^{10} = 1024$). This leaves 6 bits ($16 - 10$) in each code unit available for our control flags (x).

This math dictates the physical bit structure of UTF-16 surrogate pairs:

Lead (High) Surrogate:  110110yy yyyyyyyy  (spanning D800 to DBFF)
Trail (Low)  Surrogate:  110111yy yyyyyyyy  (spanning DC00 to DFFF)

Because these flag headers are fixed values, the code units fall into specific numeric ranges. Since they occupy physical space in the BMP, 2,048 positions (1,024 for lead units and 1,024 for trail units) had to be permanently reserved and excluded from character assignment.

Unicode officially reserves the block from D800 to DFFF in the BMP exclusively for UTF-16. No characters can ever be assigned to these code points.

This 2,048-word block is split exactly in half:

  • The first 1,024 values (D800 to DBFF) represent high surrogates (lead code units);
  • The subsequent 1,024 values (DC00 to DFFF) represent low surrogates (trail code units).

Together, they form a surrogate pair, allowing UTF-16 to access the supplementary planes.

In binary, all high surrogates (D800–DBFF) begin with the prefix 110110, while all low surrogates (DC00–DFFF) begin with 110111. This makes parsing deterministic.

To see this in action, let's look at how a parser processes the following sequence of code units:

01010101 01001010  11011000 01000000  11011100 00000000

The parser processes this stream 16 bits at a time:

  • Unit 1 (01010101 01001010): This does not begin with the 11011 surrogate prefix. The parser immediately decodes it as a standalone BMP character—specifically, the Chinese character "啊" (ah);
  • Unit 2 (11011000 01000000): This begins with 110110, flagging it as a high surrogate. The parser immediately knows this is the lead unit of a surrogate pair, and fetches the next 16 bits;
  • Unit 3 (11011100 00000000): This begins with 110111, confirming it is a valid low surrogate. The parser combines the payload bits of Unit 2 and Unit 3 to resolve a single, rare supplementary Chinese character.

The parser successfully resolves the stream into two characters: "啊" followed by the supplementary character.

The next question: how does Unicode code point U+20000 (binary: 10 00000000 00000000) map to the data bits of the two code units?

At a high level, the mapping works as follows:

  • For code points $\le \text{U+FFFF}$: The values map directly to a single code unit (except for the reserved D800–DFFF surrogate range);
  • For code points $> \text{U+FFFF}$: Split the 21-bit binary representation of the value and distribute its bits into the payload slots of a surrogate pair.

Since the Unicode codespace ceiling is 10FFFF, its binary representation spans 21 bits (1 0000 1111 1111 1111 1111). However, the combined payload space of a surrogate pair is exactly 20 bits—one bit short.

To resolve this, we subtract the offset 0x10000 (representing the BMP space) from our code point before mapping. The maximum possible value is thus $10FFFF - 10000 = FFFFF$. In binary, FFFFF is exactly 20 bits (1111 1111 1111 1111 1111), fitting perfectly into the surrogate pair payload.

The mathematical formulas for UTF-16 encoding are defined as follows:

CH = D800 + (U - 10000) / 400    (using integer division)
CL = DC00 + (U - 10000) % 400    (using modulo division)

Where CH and CL represent the decimal or hexadecimal values of the High (lead) and Low (trail) surrogate units, and U represents the source Unicode code point (all values in hex, with subscript bases omitted for readability).

To put this in plain terms: given an out-of-BMP code point $X$, subtract 0x10000. Divide the result by 0x400 (which is $1,024$ in decimal). Add the quotient to the high surrogate base D800 to yield the high code unit, and add the remainder to the low surrogate base DC00 to yield the low code unit.

Conversely, decoding a surrogate pair back to an abstract code point follows the inverse formula:

U = (CH - D800) * 400 + (CL - DC00) + 10000

Since we subtracted 0x10000 during serialization, we simply add it back on retrieval.

UTF-8

While the 16-bit design of UTF-16 was clean, its inability to natively support existing ASCII files and Unix filesystems hindered adoption. To bridge this gap, the Unicode Consortium introduced a compatible 8-bit variable-width format: UTF-8.

(Because UTF-8's fundamental code unit is exactly 8 bits wide, we will use the terms "byte" and "code unit" interchangeably in this section.)

UTF-8 represents the entire Unicode codespace using sequences of one to four bytes. Since it is a variable-length format, each byte must carry both data bits and control flags (conceptualized as xxxyyyyy). The control flags must satisfy several architectural goals:

  1. They must be instantly identifiable by parser logic;
  2. Because a character can span anywhere from one to four bytes, the flags in the leading byte must explicitly declare the total length of the sequence;
  3. The bit pattern of a sequence's leading byte must differ from its subsequent continuation bytes, ensuring the parser can determine the start of a character block from any arbitrary point in a file;
  4. The format must be completely backward-compatible with ASCII — meaning any standard ASCII character must map to a single, unmodified byte.

This is accomplished using the following bit-allocation rules:

  • Inspect the Most Significant Bit (MSB): If the highest bit is 0, it is a single-byte ASCII character. This maintains perfect parity with ASCII, where the MSB is always 0.
  • Detect Multi-Byte Sequences: If the MSB is 1, the character spans multiple bytes. To prevent parser synchronization errors, a leading byte always begins with the prefix 11, whereas all trailing continuation bytes begin with the prefix 10.
  • Declare Sequence Length: The number of consecutive 1 bits at the start of a leading byte denotes the total byte count of the character. For example, a lead byte starting with 1110xxxx flags a 3-byte sequence (common for CJK ideographs).

To summarize: the MSB acts as a single-byte vs. multi-byte gate. For multi-byte characters, the prefixes 11 and 10 cleanly separate lead bytes from trail bytes, and the count of leading 1s defines the sequence boundaries.

For example, how does a parser process the raw byte stream 01100001 11100101 10010101 10001010?

  • Byte 1 (01100001): The highest bit (MSB) is 0 → standalone ASCII character → parsed as the Latin letter "a".
  • Byte 2 (11100101): The highest bit is 1 → multi-byte character. The top two bits are 11 → lead byte of a multi-byte sequence. Counting the leading 1s reveals a three-byte character prefix (1110). The parser immediately scans the next two bytes.
  • Bytes 3 and 4 (10010101 and 10001010): Both bytes begin with the 10 prefix, confirming they are valid continuation bytes. The parser extracts the payload bits from all three bytes to resolve a single character—the Chinese character "啊" (ah).

How does the abstract code point for "啊" (U+554A) translate physically into these multi-byte code units?

We can map this process intuitively using the standard UTF-8 conversion template:

Unicode Codespace Range | UTF-8 Bit Template                  | Byte Width
------------------------|-------------------------------------|-----------
U+0000 to U+007F        | 0xxxxxxx                            | 1 byte
U+0080 to U+07FF        | 110xxxxx 10xxxxxx                   | 2 bytes
U+0800 to U+FFFF        | 1110xxxx 10xxxxxx 10xxxxxx          | 3 bytes
U+10000 to U+10FFFF     | 11110xxx 10xxxxxx 10xxxxxx 10xxxxxx | 4 bytes

The serialization algorithm is simple: extract the raw binary bits of the abstract code point and map them sequentially into the placeholder x slots of the selected byte template.

The code point for "啊" is U+554A, which is represented in binary as the 16-bit value 01010101 01001010. Referencing our template table, a 16-bit address falls within the U+0800–U+FFFF range, selecting the 3-byte template. This template has 24 bits total; subtracting the 8 prefix flag bits (1110, 10, 10) leaves exactly 16 bits of payload space:

11100000 10000000 10000000   (3-Byte UTF-8 Template)
  +
     0101 010101 001010        (Raw Binary Bits of U+554A)
  =
11100101 10010101 10001010   (Resulting UTF-8 Bytes: E5 95 8A)

While the conversion logic can also be expressed through formal algebra (using bitwise shifts and masks), this direct bit-substitution model represents the physical reality of the UTF-8 format.

UTF-32

The third format is UTF-32. It is the simplest fixed-width implementation, mapping every Unicode code point to a single 32-bit (4-byte) code unit. Because a 32-bit integer accommodates the maximum Unicode address, no flag bits or variable offsets are required.

For the Chinese character "啊" (U+554A, binary: 01010101 01001010), its UTF-32 representation is simply a 4-byte padded integer: 00000000 00000000 01010101 01001010 (ignoring byte order for the moment).

However, because its code unit is 32 bits wide, UTF-32 cannot maintain backward compatibility with 8-bit ASCII. Combined with its storage overhead, this has relegated UTF-32 to internal, in-memory use in databases and compilers where $O(1)$ string indexing is required.

Byte Order (Endianness) and the BOM

As outlined in the article on the character encoding model, physical data serialization must account for CPU endianness. This concerns only multi-byte code units (UTF-16 and UTF-32); single-byte encodings (UTF-8) are unaffected by byte order.

Using the Chinese character "啊" as an example, its representations at the Character Encoding Form (CEF) layer are structured in memory as:

UTF-8:    E5 95 8A                  (3 code units, 1 byte each — no endianness concerns)
UTF-16:   55 4A                     (1 code unit, 2 bytes wide — byte order matters)
UTF-32:   00 00 55 4A               (1 code unit, 4 bytes wide — byte order matters)

Because UTF-8 processes data strictly as a sequential stream of single bytes, there is no endianness ambiguity.

However, because a UTF-16 or UTF-32 code unit is wider than a single byte, we must declare how those bytes are serialized to disk or sent over a network:

Big-Endian (BE) stores the most significant byte first (at the lower memory address). By contrast, Little-Endian (LE) writes the least significant byte first. Factoring in endianness, our character "啊" translates to distinct physical byte sequences:

UTF-16 BE:  55 4A
UTF-16 LE:  4A 55
UTF-32 BE:  00 00 55 4A
UTF-32 LE:  4A 55 00 00

Why is this critical? When a text editor reads a file from disk, it has no way to determine which byte order the writing system used.

To resolve this, the Unicode standard reserves a special non-character code point: the ZERO WIDTH NO-BREAK SPACE (U+FEFF). Multi-byte encoding schemes (UTF-16 and UTF-32) write this character at the beginning of the file as an explicit signature.

Let's look at how U+FEFF is serialized across different formats:

UTF-8:     EF BB BF
UTF-16 BE: FE FF
UTF-16 LE: FF FE
UTF-32 BE: 00 00 FE FF
UTF-32 LE: FF FE 00 00

By inspecting the first few bytes of an incoming file, a parser can immediately deduce its structure.

If the parser encounters FE FF at the offset, it configures itself for UTF-16 Big-Endian. If it encounters FF FE, it configures itself for UTF-16 Little-Endian.

But how does the parser know that FF FE represents Little-Endian and not the Big-Endian serialization of U+FFFE? The standard explicitly designates U+FFFE as a permanent non-character. Because U+FFFE can never legally appear in text, there is no risk of collision.

This leading signature is known as the BOM (Byte Order Mark).

UTF-8 has no native endianness and never requires a BOM. However, some Windows text editors (notably Notepad) write a UTF-8 BOM (EF BB BF) to flag the file as UTF-8 rather than a legacy code page.

Warning: A UTF-8 BOM can cause serious errors in non-Windows environments. The PHP engine does not strip the BOM; it treats EF BB BF as text characters. In PHP-FPM, the BOM is flushed to the browser immediately on script execution. Because HTTP headers (cookies, redirects) cannot be sent after output begins, this silently breaks session cookies and redirects. Always configure your editor to save files as "UTF-8 without BOM."
