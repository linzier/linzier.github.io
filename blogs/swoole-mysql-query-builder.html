Swoole in Practice: Building a MySQL Query Builder with Coroutine Connection Pool

2020-05-02 | PHP/Swoole

Swoole introduced coroutines to PHP, fundamentally shifting how developers approach concurrency. However, this power demands rigorous design—particularly when managing database connections. A naive MySQL client integration within a Swoole coroutine environment quickly succumbs to connection contention, race conditions, and resource leaks. In this article, we will walk through the design and implementation of a robust MySQL query builder equipped with coroutine connection pooling, transaction isolation, pro-active health checks, and automatic recovery.

Requirements

Before diving into the implementation, let's establish our core design requirements:

  1. Chain-style SQL building. The API should feel natural: Query::table('users')->where('age', '>', 18)->orderBy('created_at', 'desc')->get(). Fluent interfaces significantly reduce cognitive overhead and make queries highly readable.
  2. Connection pooling. Creating a new MySQL connection for every query is expensive. We need a pool of pre-established connections that coroutines can borrow and return.
  3. Coroutine-safe transactions. In a coroutine environment, multiple coroutines share the same process. A transaction must be strictly bound to both a specific connection and a specific coroutine, ensuring Coroutine A’s transaction context never leaks into Coroutine B.
  4. Health checks. Connections can go stale (MySQL’s wait_timeout, network issues). The pool must detect dead connections and remove them before handing them to a caller.
  5. Automatic reconnection. When a connection drops, the system should transparently reconnect without the caller needing to handle retry logic.

Module Design

The system is divided into four modules, each with a single responsibility:

1. Query Module

The entry point for all database operations. This module provides the fluent API for building SQL queries. It delegates the actual SQL construction to a Builder trait and uses the Connection Pool to obtain connections for execution.

Key responsibilities:

  • Provide a fluent interface for SELECT, INSERT, UPDATE, DELETE
  • Manage query state (table, conditions, ordering, limits, joins)
  • Obtain connections from the pool, execute queries, return connections
  • Support both single-row and multi-row result fetching

2. Transaction Module

Handles transaction lifecycle management with coroutine isolation. Each transaction operates on a dedicated connection that is reserved for the duration of the transaction.

Key responsibilities:

  • Begin, commit, and rollback transactions
  • Ensure each coroutine gets its own isolated transaction context
  • Prevent connection reuse while a transaction is active
  • Auto-rollback on exception or coroutine exit

3. Connection Pool Module

Manages a pool of MySQL connections with separate read and write pools. The pool handles connection lifecycle, health checking, and capacity management.

Key responsibilities:

  • Maintain separate pools for read replicas and write master
  • Implement borrow/return semantics with coroutine channels
  • Perform periodic health checks on idle connections
  • Enforce pool size limits and handle connection timeouts
  • Support graceful shutdown (drain and close all connections)

4. Connector Module

The lowest-level module, responsible for establishing and maintaining individual MySQL connections. It handles the wire protocol, authentication, and automatic reconnection.

Key responsibilities:

  • Establish connections using Swoole’s coroutine MySQL client
  • Detect connection failures and trigger reconnection
  • Provide a clean interface for sending queries and receiving results
  • Track connection state (idle, in-use, broken)

Entry Point: The Query Class

The Query class is the primary interface that application code interacts with. It uses a Builder trait to provide the fluent API:

// Basic select
$rows = Query::table('users')
    ->where('status', 'active')
    ->where('age', '>=', 18)
    ->orderBy('created_at', 'desc')
    ->limit(20)
    ->get();

// Insert
$id = Query::table('orders')->insert([
    'user_id' => 42,
    'amount'  => 99.99,
    'status'  => 'pending',
]);

// Update
Query::table('users')
    ->where('id', 42)
    ->update(['status' => 'inactive']);

// Delete
Query::table('sessions')
    ->where('expired_at', '<', time())
    ->delete();

The Builder trait handles SQL string construction and parameter binding. It never touches connections directly — that is the Query class’s responsibility.

Transaction Management: CoTransaction and TContext

Managing transactions in a coroutine-driven architecture requires special care. The fundamental constraint is that a transaction must be tied to both a dedicated connection and a specific coroutine execution flow. If Coroutine A initiates a transaction on Connection 1, Coroutine B must be prevented from utilizing Connection 1 until Coroutine A's transaction is finalized.

To enforce this, we introduce two architectural components:

CoTransaction manages the transaction lifecycle. When you call CoTransaction::begin(), it borrows a dedicated connection from the write pool, marks it as “in transaction,” and stores it in the coroutine-local context. All queries within this coroutine automatically use this connection until the transaction commits or rolls back.

TContext (Transaction Context) provides coroutine-local storage. Each Swoole coroutine has its own isolated context, so transactions in different coroutines never interfere with each other, even though they share the same process memory.

// Transaction usage
CoTransaction::begin();
try {
    Query::table('accounts')
        ->where('id', $fromId)
        ->update(['balance' => new Expression('balance - 100')]);

    Query::table('accounts')
        ->where('id', $toId)
        ->update(['balance' => new Expression('balance + 100')]);

    Query::table('transfers')->insert([
        'from_id' => $fromId,
        'to_id'   => $toId,
        'amount'  => 100,
    ]);

    CoTransaction::commit();
} catch (\Throwable $e) {
    CoTransaction::rollback();
    throw $e;
}

Connection Pool: CoPool

The connection pool is the heart of the system. It uses Swoole’s Chan (coroutine channel) to implement a blocking, thread-safe pool.

Design decisions:

  • Separate read and write pools. Write operations go to the master; read operations go to replicas. This enables read-write splitting at the connection pool level.
  • Channel-based borrowing. The pool is implemented as a Swoole Channel. Connections are pushed into the channel when idle. Borrowing a connection is a pop() operation, which blocks the coroutine if no connections are available (rather than blocking the entire process).
  • Health checks on borrow. Before handing a connection to the caller, the pool sends a PING to verify the connection is alive. Dead connections are discarded and replaced.
  • Idle timeout. Connections that sit idle for too long are closed to free MySQL resources. The pool maintains a minimum size and will create new connections on demand up to the maximum size.
// Pool configuration
$pool = new CoPool([
    'write' => [
        'host'     => 'master.db.internal',
        'port'     => 3306,
        'user'     => 'app',
        'password' => '***',
        'database' => 'myapp',
        'min'      => 5,
        'max'      => 20,
    ],
    'read' => [
        'host'     => 'replica.db.internal',
        'port'     => 3306,
        'user'     => 'app_ro',
        'password' => '***',
        'database' => 'myapp',
        'min'      => 10,
        'max'      => 50,
    ],
]);

Connector: CoConnector with Auto-Reconnect

Each CoConnector wraps a single Swoole coroutine MySQL client. It provides a clean interface for executing queries and handles reconnection transparently.

The reconnection logic works as follows:

  1. Before executing a query, check if the connection is alive.
  2. If the connection is dead, attempt to reconnect (up to N retries with exponential backoff).
  3. If reconnection succeeds, retry the query.
  4. If reconnection fails after all retries, mark the connection as broken and throw an exception. The pool will discard this connection and create a replacement.

This means that application code never needs to handle connection failures. The connector absorbs transient network issues and MySQL restarts without the caller knowing.

Factory Assembly

A factory class wires everything together. Application code initializes the factory once at startup, and the factory creates the pool, connectors, and query instances:

// Bootstrap (typically in a Swoole server start callback)
DbFactory::init($config);

// Then anywhere in your coroutine code:
$rows = Query::table('users')->where('id', 42)->first();

The factory reads configuration, creates the connection pool, warms it up to the minimum size, and registers it as the global default. From that point on, Query calls automatically draw connections from the pool.

Lessons Learned

Designing and deploying this system highlighted several critical insights regarding Swoole's coroutine model:

  • Coroutine safety requires intentional design. Sharing resources across asynchronous execution threads demands robust isolation layers. Connection pools, transaction contexts, and even global state must be entirely coroutine-aware.
  • Channels are powerful. Swoole’s Chan is the fundamental building block for coroutine-safe data structures. If you understand channels, you can build almost any concurrent primitive.
  • Health checks are non-negotiable. In long-running daemon processes, network connections inevitably go stale. Without reliable health checks, your application will suffer from intermittent failures on initial queries following idle periods.
  • Separation of concerns pays off. By splitting the system into Query, Transaction, Pool, and Connector modules, each piece is independently testable and replaceable.

Summary

We designed and implemented a MySQL query builder for Swoole that addresses the unique challenges of coroutine-based database access. The four-module architecture — Query, Transaction, Pool, and Connector — provides a clean separation of concerns while delivering chain-style SQL building, coroutine-safe connection pooling, isolated transactions, health checks, and automatic reconnection.

The result is a database layer that feels as natural to use as Eloquent or Doctrine, but is built from the ground up for Swoole’s coroutine environment.
