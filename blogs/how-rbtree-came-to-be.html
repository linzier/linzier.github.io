How Red-Black Trees Came to Be

2023-05-22 | Data Structures

The Key to Balance

In the previous article, The Essence of Binary Search Trees, we identified a serious practical problem with binary search trees: tree skew. Inserting data in a particular order can cause the tree to degenerate into a linked list, degrading all operations to O(n).

How can we keep the tree balanced after write operations?

Professor R sat sipping his black coffee, staring intently at this "deformed," skewed binary search tree.

"How can we insert new nodes without destroying the tree's balance?"

Then it clicked.

"That is the core issue: the tree always grows downward." Professor R realized that every time a new node is inserted, it is appended as a child under an existing leaf, increasing the tree's height by one.

"So, what if we prevent the tree from growing downward?"

For example, when inserting element 2, instead of making it a child of node 1, what if we put it together with 1?

The tree stops growing in height. But a new problem emerges: if we keep squeezing every new element into the same node, the tree collapses into a single giant node and degenerates back into an array.

"Since it must grow, but cannot grow downward, its only choice is to grow upward!"

When the number of elements in a single node reaches three, we perform a split: the middle element is pushed up to become the parent P, and the remaining two elements become its left and right children.

A node containing three elements splits into three independent nodes, raising the height of that subtree by one.

In a standard binary search tree, each node has at most two children. In our new balanced tree, a node holds up to two elements. A node with two keys, a and b, partitions the key space into three intervals and can have two or three children. This structure is called a 2-3 Tree.

Inserting elements 1 through 11 in order shows how the 2-3 tree maintains its balance:

Only one situation increases tree height: splitting the root. This process is symmetric, so the entire tree remains balanced regardless of how splits occur.

The Problem with 2-3 Trees

Professor R hit a wall during implementation: this seemingly elegant data structure proved extraordinarily difficult to code.

Hearing his frustrations, Professor L smiled and sketched on a napkin: "Don't fret. Whether it's a 2-node or a 3-node, they are logically equivalent. In fact, we can represent any 2-3 tree using a simple binary tree!"

Red lines mark the relationship between the two elements within a 3-node, allowing 2-nodes to represent 3-nodes.

Transfer the edge color to the lower node, yielding a tree with two node types: red and black.

Properties of Red-Black Trees

Property 1: No two consecutive red nodes are allowed.

Property 2: Every simple path from any leaf to the root contains the same number of black nodes.

Property 3: The root node is black.

Property 4: A red node must be the left child of its parent. (Left-leaning red-black tree)

Summary

  1. Root Cause of Skew: Standard binary search trees skew because new nodes are always appended as leaves (downward growth).
  2. Preventative Strategy: To maintain balance, we changed the growth direction—adopting a split-based, upward growth strategy.
  3. The 2-3 Tree: This upward-growth strategy produced the 2-3 Tree, which maintains perfect balance through root-level splitting.
  4. The Red-Black Tree: To simplify the implementation complexity of 2-3 Trees, we mapped them to binary trees with red and black links.
  5. Left-Leaning RB Trees: By standardizing 3-nodes as left-leaning red nodes, we distilled four core properties of Left-Leaning Red-Black (LLRB) trees.
  6. Core Operations: All red-black tree invariants can be maintained with just three local, constant-time operations: left rotation, right rotation, and color flipping.
