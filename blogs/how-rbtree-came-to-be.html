How Red-Black Trees Came to Be

2023-05-22 | Data Structures | Original

The Key to Balance

Picking up where we left off — in the previous article, The Essence of Binary Search Trees, we mentioned a serious practical problem with binary search trees: tree skew. Inserting data in a particular order can cause a binary search tree to degenerate into a plain linked list, degrading all operations to O(n) time complexity.

How can we keep the tree balanced after write operations?

Professor R sat sipping his black coffee, staring at this "deformed" binary tree.

"How can we add new nodes without destroying the tree's balance?"

Suddenly, his eyes lit up!

"Yes! That's the problem: growing downward." Professor R realized that every time we add a new node, we create a new child under an existing leaf. Each new node increases the tree height by 1.

"Then what if we stop the tree from growing downward?"

For example, when inserting element 2, instead of making it a child of node 1, what if we put it together with 1?

Now the tree stops growing in height. But there's a problem: if the entire tree collapses into a single node, haven't we just regressed to an array?

"Since it needs to grow, but can't grow downward, it can only grow upward."

When the number of elements in a node reaches 3, we take the middle element as the parent P, and the two remaining elements become P's left and right children.

The original node containing 3 elements splits into three nodes, and the height of the subtree rooted at that node increases by 1.

In a binary search tree, each node P can have at most 2 children. In our new search tree, a node can hold up to 2 elements. When a node has 2 elements a and b, it can represent 3 intervals. So a node can have 2 or 3 children. We call this a 2-3 tree.

Let us insert elements 1 through 11 in order and see what the resulting 2-3 tree looks like.

Only one situation increases the tree height: splitting of the root node. This process is symmetric, so no matter how the splits occur, the entire tree remains balanced.

The Problem with 2-3 Trees

Professor R ran into trouble during implementation. This seemingly simple data structure turned out to be extremely complex to code.

Professor L explained: "Whether it's a 2-node or a 3-node, they are logically equivalent. We can represent a 2-3 tree using a binary tree!"

Use red lines to mark the relationship between the two elements within a 3-node. This way, we can use 2-nodes to represent 3-nodes.

We can transfer the edge color to the lower node, giving us a tree with two types of nodes: red and black.

Properties of Red-Black Trees

Property 1: No two consecutive red nodes are allowed.

Property 2: Every simple path from any leaf to the root contains the same number of black nodes.

Property 3: The root node is black.

Property 4: A red node must be the left child of its parent. (Left-leaning red-black tree)

Summary

  1. Identified the cause of binary tree skew: downward growth;
  2. Strategy to prevent skew: change the growth direction — adopt a split-based upward growth strategy;
  3. From point 2, the 2-3 tree evolved naturally;
  4. Due to the implementation complexity of 2-3 trees, red-black trees were introduced;
  5. Based on 2-3 tree properties, we distilled 4 properties of left-leaning red-black trees;
  6. Based on binary search tree properties, we discovered three core operations: left rotation, right rotation, and color flip;
