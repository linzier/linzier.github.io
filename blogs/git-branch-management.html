Git Branch Management in Practice

2020-04-23 | Process

Overview

Effective branch management is the backbone of a smooth development workflow. After years of trial and error, our team settled on a branching model with four distinct branch types, each serving a specific purpose. This article describes the model and the reasoning behind it.

The Four Branch Types

  • feature/fix branches — temporary branches for developing individual features or bug fixes.
  • test branch — a permanent integration branch where all features are combined for testing.
  • release branches — snapshots prepared for pre-production verification and deployment.
  • master branch — mirrors production code at all times.

Feature/Fix Branches

Purpose

Feature branches are where development happens. Each requirement or bug fix gets its own branch, isolated from all other work.

Naming Convention

feature-<developer>-<description>

For example: feature-zhangsan-user-auth or fix-lisi-payment-bug.

Lifecycle

  1. Branch from the latest master.
  2. Develop and commit locally.
  3. Regularly merge the latest master into the feature branch to stay current.
  4. When development is complete, merge into the test branch for integration testing.
  5. After testing passes, the feature branch is merged into the release branch (or directly into master for small teams).
  6. The feature branch is deleted after its content is merged and deployed.
Feature branches are temporary. They exist only for the duration of development and should be deleted promptly after merging.

Test Branch

Purpose

The test branch is a permanent integration branch. It is the staging area where all features in the current testing cycle are combined. QA deploys from this branch to the test environment.

Characteristics

  • It is long-lived, unlike feature branches.
  • Multiple feature branches are merged into it as they complete development.
  • It may contain features that are at different stages of testing.
  • It is reset (rebuilt) at the start of each release cycle.

The Pollution Problem

Since the test branch aggregates features from multiple developers, it inevitably becomes "polluted" over time—a state where merge conflicts, broken builds, or unstable code render the environment unreliable for QA. When pollution sets in, the only clean solution is to rebuild the test branch from scratch:

  1. Delete the current test branch.
  2. Create a new test branch from the latest master.
  3. Re-merge only the feature branches that are still valid and ready for testing.

This is a painful but necessary operation. It underscores the importance of keeping feature branches clean and well-tested before merging into test.

Release Branches

Purpose

Release branches are created from master to prepare a specific deployment. They represent a frozen snapshot of the code going to production, allowing final verification in a pre-production environment.

Naming Convention

release-YYYYMMDD.NN

For example: release-20200423.01. The NN suffix allows multiple releases on the same day if needed.

Lifecycle

  1. Create the release branch from the latest master.
  2. Merge the feature branches that have passed testing into the release branch.
  3. Deploy the release branch to the pre-production (staging) environment.
  4. Conduct final verification (smoke tests, regression tests, performance tests).
  5. Fix any last-minute bugs directly on the release branch (these fixes must also be merged back to master).
  6. Once approved, deploy the release branch to production.
  7. After successful deployment, merge the release branch back into master and tag it.

Master Branch

Purpose

The master branch is the single source of truth for what is running in production. At all times, the state of master should match the production environment.

Rules

  • Never develop directly on master. All changes must come through feature branches, test integration, and release branches.
  • Only merged release branches and hotfixes should modify master.
  • Every commit on master should be tagged with a version number.
  • master is protected: direct pushes are disabled, and all changes must go through pull requests with required reviews.

Why Release Branches Instead of Deploying Master Directly?

A common question: why bother with release branches? Why not merge everything into master and deploy from there?

There are two key reasons:

1. Isolation

A release branch isolates the code about to be deployed from ongoing development. While the release branch is verified and deployed, developers continue working on new features that merge into test without affecting the release. Deploying directly from master would require freezing development during the release process.

2. Parallel Deployments

Sometimes you need to prepare multiple releases in parallel—a routine sprint deployment and an urgent hotfix, for example. Release branches let you prepare and deploy them independently. Without them, managing parallel deployments from a single master branch becomes chaotic.

Handling Release Coverage Issues

One common challenge with the release branch model is the "leakage" problem: when preparing a release, newer features excluded from this cycle may already be merged into the test branch. If you cut the release branch from test instead of master, those unapproved features will leak into your production candidate.

The solution is a management process:

  1. Release branches are always created from master, never from test.
  2. Feature branches are merged into the release branch selectively — only features that have passed QA testing are included.
  3. The release manager maintains a checklist of which features are included in each release.
  4. Any feature not on the checklist is excluded, even if it has been merged into test.

This requires discipline, but it is far better than accidentally deploying untested code to production.

Summary

The four-branch model — feature, test, release, master — provides a clear separation of concerns:

  • Feature branches isolate development work.
  • The test branch provides a shared integration environment for QA.
  • Release branches create safe, isolated snapshots for deployment.
  • Master remains a pristine mirror of production.

No branching model is perfect, and this one requires discipline. After years of practice, we have found that it balances flexibility and control, allowing teams to move fast without sacrificing stability.
